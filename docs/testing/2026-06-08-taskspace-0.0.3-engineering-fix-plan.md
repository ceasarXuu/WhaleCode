# TaskSpace 0.0.3 工程阻塞修复计划

## 背景

TaskSpace 0.0.2 的 P0 E3 重跑暴露了一个工程级 blocker：Terminal-Bench public validator 在 Docker 内运行时，部分验证进程已经产出 pair report 和 aggregate，但 Docker 容器仍然处于 `Up` 状态，父级 benchmark driver 被遗留的 `wsl.exe docker run` 阻塞，必须人工 `docker stop` 后才能继续。

这说明当前 E3 harness 不能稳定地产生完整、可审计的结果。0.0.3 的目标不是证明 TaskSpace 有正收益，而是先修复执行基建，使后续 E3 结果不会被基础设施卡死和环境噪声污染。

## 根因假设

1. `Invoke-TaskspaceValidationCommand` 只负责运行 validator 和把 timeout 转成 `124`，没有 run-specific cleanup hook。
2. Terminal-Bench adapter 生成的 validator 虽然有 `finally { docker rm -f ... }`，但当父进程 timeout 或 Windows/WSL 进程树断开时，validator 自身的 `finally` 不一定可靠执行。
3. Docker 清理只存在于 validator 子进程内部，缺少父级兜底；一旦子进程被杀，Docker 容器和 `docker run` 进程可能继续运行。
4. 当前 cleanup 证据散落在 stdout/stderr/runtime manifest 中，缺少统一的 timeout cleanup 结果记录，后续人工复核难以判断环境失败和业务失败的边界。

## 修复目标

### 必须修复

- 父级 validation runner 在 timeout 或 validator 退出后，都能执行 run-specific Docker cleanup。
- cleanup 只能作用于当前验证对应的容器，不能按宽泛 label 清理其他 benchmark run。
- cleanup 结果必须写入 validator artifact，包含容器名、repo hash、触发原因、stop/rm exit code、时间戳。
- timeout 仍然 fail-closed，公共验证返回 `124`，不能被 cleanup 成功掩盖。
- pair report 和 aggregate 能明确看到 validator environment failure，而不是静默进入 clean E3。

### 暂不解决

- 不优化 TaskSpace 规划效果，不调整 agent-map 行为模式。
- 不把网络依赖离线化为完整 runner 镜像；本轮只把网络导致的 timeout 变成可控失败。
- 不宣称 E3 达成，只恢复可重复执行能力。

## 工程设计

### 1. Validation cleanup contract

在 public validation manifest 上新增可选 `cleanup` contract，由 adapter 生成：

cleanup 不写死到 scenario manifest，因为真实 repo path 在 pair materialization 后才确定。Terminal-Bench validator 在运行时生成：

- run-unique container: `whale-tbench-<repoHash>-<proofNoncePrefix>`
- run-unique image: `whale-taskspace-terminal-bench:<repoHash>-<proofNoncePrefix>`
- labels: `whale.taskspace.repo_hash`、`whale.taskspace.proof_nonce`、`whale.taskspace.proof_dir_hash`
- runtime manifest: `ProofDir/terminal-bench-runtime-manifest.json`

父级 runner 在 timeout 或 validation 结束后读取 runtime manifest，再通过 `docker inspect` 校验 labels 与 manifest 一致，只有身份匹配时才执行 `docker rm -f`。

### 2. 父级 timeout cleanup

`Invoke-TaskspaceValidationCommand` 捕获 timeout 后：

1. 保持 stdout/stderr timeout 记录。
2. 调用 `Invoke-TaskspaceValidationCleanup -ProofDir $ProofDir -Reason "timeout"`。
3. cleanup 读取 runtime manifest 中的 `container_name`、`image`、`docker_backend`。
4. 校验 container name 格式与 labels 身份。
5. 只对身份匹配的容器执行 `docker rm -f <container_name>`。
6. cleanup no-throw：任何 cleanup 异常都只写 artifact，不覆盖原 validation exit code。
7. 不删除宽泛 label 下的其他容器。

正常退出后也执行同一 cleanup，reason 为 `post_validation`，用于处理 validator 内部 finally 失败的情况。

### 3. Evidence logging

新增 `validation-cleanup-result.json`：

```json
{
  "schema_version": 1,
  "reason": "timeout",
  "proof_dir": "...",
  "container_name": "whale-tbench-...",
  "image": "whale-taskspace-terminal-bench:...",
  "docker_backend": "wsl",
  "rm_exit_code": 0,
  "cleanup_attempted": true,
  "timestamp": "..."
}
```

同时在 stderr 追加一行 cleanup result path，便于 pair report 证据串联。

### 4. 测试策略

- `test-oracle-runner-harness.ps1`：扩展 fake validation proof，模拟 timeout 后存在 runtime manifest，验证 cleanup result 被写入且 validation exit code 仍为 `124`。
- `test-terminal-bench-adapter-harness.ps1`：验证生成的 validator runtime manifest 仍包含 container/image/backend 信息，保证父级 cleanup 有入口。
- `test-harness.ps1` / E3 proof 相关测试：验证 cleanup proof 不会让 timeout 变成 clean E3。
- 真实执行：先跑一个小范围 Terminal-Bench sample，确认 run 结束后无 `whale.taskspace.terminal_bench=true` 遗留容器，再记录为 0.0.3。

## 对抗审查关注点

- Windows 上 `Process.Kill(true)` 是否能可靠杀掉 PowerShell -> WSL -> Docker 进程树。
- 父级 cleanup 是否可能误杀其他正在运行的 E3 run。
- cleanup 成功是否会掩盖 validator timeout 或 public validation failure。
- 证据是否足够支持后续人工复核。
- 测试是否真的覆盖 timeout 后的 cleanup，而不是只覆盖正常路径。
