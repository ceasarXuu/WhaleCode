# Codex CLI 0.147 候选资格验证

## 结论

Codex CLI `rust-v0.147.0` / `be6e8eac029b183056b7e4402879f15d2c85f61b` 的 U2 Checkpoint A 结论为 `direction-rejected`。本轮不重算 overlay/delta/replay 工件，不执行 U3，也不替换生产 vendor。

阻断点不是 DeepSeek 或 TaskSpace 冲突，而是固定上游候选自身的 Linux 构建闭环不完整：`code-mode-runtime` 启用 `v8_enable_sandbox`，要求 rusty_v8 `v150.4.0` 的 `librusty_v8_ptrcomp_sandbox_release_x86_64-unknown-linux-gnu.a.gz`；该 release 的 74 个资产中不存在此文件，直接下载 URL 返回 HTTP 404。因此 `codex-code-mode-host` 无法通过正常预编译 V8 路径构建，并连带污染 core/app-server 的 code-mode 测试。

## 验证边界

- 固定候选 commit 与 tree：`be6e8eac029b183056b7e4402879f15d2c85f61b` / `3828c818254d4c756585f5b59fe46b6fa3634765`；
- 独立 `git archive` 临时树，生产 vendor index tree 前后均为 `7bcedd04a466e407dd160b7c541fe13605c2d4ec`；
- user namespace、bubblewrap、PTY、Unix IPC 与 loopback TCP 前置能力均通过；
- 0 次模型请求，没有真实 Whale Agent run。

## Runner 治理

首轮矩阵暴露了三个 runner 问题：未按官方流程预取依赖、helper 晚于 core 构建、构建阶段错误清除了系统代理。已做最小修正：

1. 在候选临时树先执行官方同口径的 `cargo fetch`；
2. 先构建 sibling `codex-code-mode-host`，再执行 core/app-server 测试；
3. 依赖预取与构建继承系统代理，包测试继续清除 proxy 环境，避免本机代理污染网络隔离断言；
4. candidate target 与旧 overlay target 分离；候选被拒绝时不让 0.146 的历史 delta/replay 工件变成伪过期。

同步脚本 37 项单测覆盖上述命令、环境和 target 分离约束。

## 最终资格矩阵

| 检查 | 结果 | 归因 |
| --- | --- | --- |
| `cargo fmt --all -- --check` | passed | 候选格式正常 |
| offline CLI check | passed | 依赖预取后通过，首轮失败确认为 runner 顺序问题 |
| code-mode-host build | failed | rusty_v8 所需 sandbox 资产缺失，发布 URL 404 |
| core nextest | failed | 3,160 passed、133 failed、1 timeout、8 skipped；主要受 helper 缺失及本地 MCP/CLI 子进程路径污染，不能覆盖独立的 helper no-go |
| app-server nextest | failed | 1,112 passed、7 failed、1 skipped；失败集中于 code-mode/MCP capability 路径，受 helper 缺失连带影响 |
| TUI nextest | failed | 3,370 passed、38 failed、1 timeout、4 skipped；主要是 `0.0.0 -> 0.147.0` release snapshot 机械差异，另有 IDE IPC 失败/超时 |

这里不把 snapshot 的 `0.0.0` 当作候选缺陷；真正独立成立的 no-go 是缺失的 rusty_v8 sandbox 发布资产。也不通过修改候选 Cargo feature、伪造 archive 或本地编译 V8 来改变固定候选资格。
