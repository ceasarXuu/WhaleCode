- Created: 2026-07-25
- Version: 1.2
- Status: Adversarially reviewed; pending product decision
- Risk: High
- Scope: R-10；L4 Tool Contract 与对应 L5 机械执行/反馈
- Previous milestone:
  [`40-r7.1-milestone-baseline.md`](40-r7.1-milestone-baseline.md)
- Integrated constraints:
  [`38-r7-five-layer-integrated-change-constraints.md`](38-r7-five-layer-integrated-change-constraints.md)
- Implementation status: Not started

## 1. 决策摘要

R7.1-A2 建议采用以下唯一承载方案：

1. `bind_node` 与 `complete_then_continue` 从中央 `taskspace_control` 移到普通 Tool 的必填
   `taskspace_binding` 判别联合中。
2. lifecycle 参数与该普通 Tool 的原生业务参数属于同一个 Tool call。Agent 不再能够通过 provider-visible
   schema 表达一个没有普通 Tool 调用的非终态 boundary。
3. `after_boundary` 分支、中央同名 action 及其跨兄弟调用 sequence pairing 一次性删除，不保留兼容 parser。
4. 普通 Tool 的业务参数、权限、sandbox、hook、approval、handler 和原生结果保持原路径；Runtime 只剥离并执行
   `taskspace_binding`。
5. `finish_map`、图变更、block/unblock/rework 和读取仍由中央 `taskspace_control` 承载。
6. 该方案提供的是**单 Tool call 的结构不可分离和提交前准入保证**，不是 Map Store 与 shell、文件系统或远端
   MCP 之间的分布式事务。

本设计完成后仍需产品确认。R7.1-A2 不修改生产代码；获得确认后才能进入 R7.1-B 单变量实现。

## 2. 问题与根因

### 2.1 当前 wire

当前非终态连续动作由两个兄弟 Tool call 表达：

```text
taskspace_control(action=complete_then_continue, ...)
ordinary_tool(taskspace_binding={"action":"after_boundary"}, ...)
```

`taskspace_control` 的 schema 只能约束自身参数，普通 Tool 的 schema 也只能约束自身参数。JSON Schema 不能从一个
数组元素要求另一个兄弟 Tool call 必须存在。当前 Runtime 因而只能在完整模型响应生成后做 sequence preflight：

- 单独 boundary：`taskspace_boundary_requires_after_boundary_action`；
- 孤立 `after_boundary`：`taskspace_after_boundary_requires_boundary_control`；
- 两者都在任何业务执行前被整响应零执行拒绝。

这种拒绝在安全上正确，但在行为上是后置惩罚：Agent 已经生成了 schema 内合法的单独 boundary，Runtime 才告知
这个跨调用组合不合法。R-10 的目标不是让拒绝更强，而是让错误形状在 L4 中不可表达。

### 2.2 已观察影响

角色分区候选 repeat-3 中，TaskSpace 18 次运行共出现 28 次 protocol failure；其中一个 `map-append`
运行在业务验证通过后连续生成 3 次单独 `complete_then_continue`，随后选中未 ready 后继，最终未闭合 Map。
旧基线也已有 25 次 protocol failure，说明该问题不是本轮偶发回归，而是现有跨 Tool schema 设计的结构缺陷。

### 2.3 根因判定

| 层 | 判定 |
|---|---|
| Agent 智能 | 可以生成合法配对，但遵循不稳定；不是第一优先根因 |
| L1/L2 | 已说明连续动作；继续增强提示词不能让跨调用约束结构化 |
| L4 | 同一个产品动作被拆成两个分别合法的 Tool call，是直接根因 |
| L5 Runtime | preflight 只能事后拒绝，不能修复 L4 表达能力 |
| projection | 与 R-10 的结构可表达性无直接因果，留给 R-22 单变量实验 |

## 3. 目标与非目标

### 3.1 目标

- 非终态 boundary 与后继普通 Tool 调用在一个 provider-visible Tool call 中不可分离。
- revision、当前节点、后继节点继续由 Agent 明确提交。
- Map 校验或提交失败时，原生业务 Tool 零执行。
- Map 提交成功后，原生业务 Tool 的成功或失败忠实返回，不回滚、不改写。
- 复用现有 ordinary Tool router 和初始化 carrier 路径，不增加通用 dispatcher 或平行架构。
- Standard 的 Tool schema、参数、router 与执行路径字节不变。
- 三种 projection policy 使用完全相同的 L4 schema 和执行实现。
- 保留同一 response 中多个无结果依赖的连续动作，以及现有单 Patch 硬门。

### 3.2 非目标

- 不修改 Map 状态机、rooted DAG、revision、readiness、lease 或 terminal 规则。
- 不让 Runtime 选择节点、补全后继、推断动作目的或自动重试。
- 不把普通 Tool 业务参数嵌入 `taskspace_control`。
- 不把 `apply_patch` 变成 JSON 字符串中的嵌套 Patch。
- 不实现跨 SQLite、进程、文件系统和远端 MCP 的分布式回滚。
- A2 设计阶段不修改 L1、L2、L3 或三种 projection policy；B 实施必须同步移除 L2 中已经失效的旧 wire
  说明，但不得借机改变宏观工作方法。
- 不在本阶段解决 R-19 固定初始化 schema 成本或 R-22 multi-Patch 行为。

## 4. 候选比较

| 候选 | 结构保证 | 业务参数保真 | Runtime 边界 | 固定成本 | 结论 |
|---|---|---|---|---|---|
| A. 保留中央 boundary + sibling | 不能；只能后置拒绝 | 保持 | Runtime 承担跨调用惩罚 | 当前基线 | 淘汰 |
| B. 把普通 Tool 完整嵌入 control | 可以 | Patch/MCP/命令易被嵌套破坏 | 形成通用 dispatcher | 中央 schema 大幅增加 | 淘汰 |
| C. 普通 Tool binding 承载 boundary | 可以；单 call 内不可分离 | 保持原生顶层参数 | 只做机械准入和提交 | 小分支复制，需实测 | **建议** |
| D. Runtime 根据业务 Tool 自动推断 boundary | 表面可以 | 保持 | Runtime 代替 Agent 选状态和节点 | 较低 | 淘汰 |
| E. 继续加强 L1/L2 文本 | 不能形成结构保证 | 保持 | 仍需后置 reject | 不变 | 淘汰 |

候选 C 是当前比较中唯一未违反 C-02、C-03、C-05、C-09、C-10、C-11、C-12 和 C-15 的首选候选，
但仍须通过 B0 schema/cost probe、B4 工程合同和 B5 准入证据才能成立。

## 5. L4 Agent 可见合同

### 5.1 唯一 binding 联合

TaskSpace 下每个可承载的普通 Tool 保留一个必填 `taskspace_binding`。联合固定为四个由 `action` 判别的对象：

```json
{
  "anyOf": [
    {
      "type": "object",
      "properties": {
        "action": { "type": "string", "enum": ["active"] }
      },
      "required": ["action"],
      "additionalProperties": false
    },
    {
      "type": "object",
      "properties": {
        "action": { "type": "string", "enum": ["initialize_map"] },
        "root": { "...": "现行角色分区初始化 schema" },
        "initial_work_node": { "...": "现行角色分区初始化 schema" },
        "finish_identity": { "...": "现行角色分区初始化 schema" },
        "additional_work_nodes": { "...": "现行角色分区初始化 schema" },
        "edges": { "...": "现行角色分区初始化 schema" }
      },
      "required": [
        "action",
        "root",
        "initial_work_node",
        "finish_identity",
        "additional_work_nodes",
        "edges"
      ],
      "additionalProperties": false
    },
    {
      "type": "object",
      "properties": {
        "action": { "type": "string", "enum": ["bind_node"] },
        "expected_revision": { "type": "integer", "minimum": 0 },
        "node_id": { "type": "string" }
      },
      "required": ["action", "expected_revision", "node_id"],
      "additionalProperties": false
    },
    {
      "type": "object",
      "properties": {
        "action": { "type": "string", "enum": ["complete_then_continue"] },
        "expected_revision": { "type": "integer", "minimum": 0 },
        "current_node_id": { "type": "string" },
        "next_node_id": { "type": "string" }
      },
      "required": [
        "action",
        "expected_revision",
        "current_node_id",
        "next_node_id"
      ],
      "additionalProperties": false
    }
  ]
}
```

实施使用 DeepSeek strict 已明确支持的 `anyOf`，每个对象所有属性均列入 `required`，并设置
`additionalProperties=false`。各分支的 `action` 枚举互斥，因此不需要依赖 DeepSeek strict 未明确承诺的
`oneOf`。

### 5.2 普通业务参数保持顶层

以下形状是唯一允许方向：

```json
{
  "cmd": "cargo test -p codex-core taskspace",
  "yield_time_ms": 30000,
  "taskspace_binding": {
    "action": "complete_then_continue",
    "expected_revision": 8,
    "current_node_id": "implement",
    "next_node_id": "verify"
  }
}
```

`apply_patch` 仍保持：

```json
{
  "input": "*** Begin Patch\n...",
  "taskspace_binding": {
    "action": "bind_node",
    "expected_revision": 3,
    "node_id": "implement"
  }
}
```

禁止引入以下形状：

```json
{
  "action": "complete_then_continue",
  "next_tool": "apply_patch",
  "next_tool_arguments": "{\"input\":\"...\"}"
}
```

### 5.3 中央 control 的目标 action 集

实施后中央 `taskspace_control` 只保留：

```text
mutate_graph
block_node
unblock_node
rework_node
finish_map
expand_nodes
read_map
read_output_ref
```

以下入口必须从 schema、wire parser、Rust enum、handler 路由、fixtures 和文档中共同删除：

```text
bind_node
complete_then_continue
after_boundary
```

初始化继续只存在于首个真实普通 Tool 的 binding，不恢复中央 `initialize_map`。

### 5.4 结构保证的准确边界

目标 schema 只能保证“非终态 boundary 必须附着在一个普通 Tool 调用上”，不能保证该调用在任务语义上有价值。
Agent 仍可能选择空查询、错误命令或无效读取；这时 Map boundary 已提交，原生 Tool 返回真实失败。判断一个合法
Tool 调用是否是有意义的后继工作属于 Agent 智能，不允许 Runtime 通过 Tool allowlist、命令内容、查询文本或
节点 goal 做语义判断。

因此 R-10 的确定性验收口径是：

- provider-visible schema 中不存在 standalone 非终态 boundary；
- 运行时不再产生 missing-sibling/orphan-after-boundary 拒绝；
- 一个携带 boundary 的普通 Tool 若自身失败，按第 8 节保留两份事实。

它不承诺 Agent 永远选择正确或有价值的普通 Tool。

## 6. 所有权与职责

| 能力 | Agent | L4 schema | Runtime/Store | 普通 Tool handler |
|---|---|---|---|---|
| 选择 boundary 类型 | 唯一负责 | 提供互斥分支 | 不推断 | 不参与 |
| 提交 revision/node | 唯一负责 | 要求字段和类型 | 校验 canonical 事实 | 不参与 |
| 选择后继真实动作 | 唯一负责 | 与 boundary 同 call | 不补动作 | 执行原生动作 |
| 校验 DAG/lifecycle | 不负责实现 | 声明合同 | 唯一机械执行 | 不参与 |
| Map commit | 不负责实现 | 不执行 | Store CAS 原子提交 | 不参与 |
| 业务参数与副作用 | 提交参数 | 保持原生字段 | 不改写 | 原生实现负责 |
| 业务结果 | 接收事实 | 定义 carrier 头 | 只并列 Map 事实 | 原样提供 |

这不是新增架构层。现有 `taskspace_binding` 从“兄弟配对标记”升级为完整的普通 Tool Map binding action；现有
初始化 carrier 扩展为共享 binding carrier。

## 7. 执行语义

### 7.1 整响应 preflight

任何调用执行前，Runtime 先完成现有整响应机械检查：

- provider 响应完整；
- 每个 Tool call 可解析；
- TaskSpace 普通 Tool 都携带合法 binding；
- 每个 response 最多一个 Patch；
- provider-native 不可承载形状仍拒绝；
- 每个 carrier 的 binding 参数可以完整解析。

删除 boundary/sibling 与 orphan `after_boundary` 的配对规则。它们不再是可能的 wire 形状。
revision、readiness 和 lifecycle 状态在每个 carrier 实际提交前按 canonical Store 事实校验，不在整响应
preflight 中预演或推测未来提交。

### 7.2 单 carrier-bound call

对 `initialize_map`、`bind_node`、`complete_then_continue`：

1. Router 从普通 Tool 参数中提取 binding，保留原生业务参数。
2. 从 canonical Map Store 读取当前 `map_id`、revision 和相关状态。
3. 解析 Agent 提交值，执行 revision、readiness、binding、lease 和 DAG/lifecycle 硬校验。
4. 构造候选 Map 变更；校验失败时不提交、不 dispatch 普通 Tool。
5. 通过 Store CAS 提交 Map 变更。
6. 仅在 commit 成功后，通过现有 Router 执行原生普通 Tool。
7. 将原生结果记录到提交后的 active node，并返回一份 carrier 事实头和原生结果。

carrier-bound call 是 sequence barrier。`active` 普通调用继续使用现有并行分段；只有 Agent 判断它们不依赖彼此
返回值时才应放在同一 response。

### 7.3 多个连续动作

同一 response 可以声明多个 carrier-bound call，按声明顺序执行：

```text
complete_then_continue + ordinary_tool_A
complete_then_continue + ordinary_tool_B
finish_map
```

每个分支都必须提交其 `expected_revision`。后一个 revision 只能基于前一个已知、确定的 Map transition 递增关系
计算；如果后续动作是否成立依赖前一个普通 Tool 的真实结果，Agent 必须等待下一次 provider request，Runtime
不得替 Agent 猜测。

失败顺序使用唯一机械规则：任一 carrier 的 Map 提交失败或原生业务 Tool 失败后，同一 response 中尚未执行的
全部调用都标记为 `skipped_due_to_prior_failure`。Runtime 不区分“语义相关”与“语义独立”。Agent 若希望一个
动作不受另一个动作失败影响，应把它们放在同一 `active` 并行段，或等待结果后在下一次 response 决定。

### 7.4 精确的原子性边界

本设计只承诺：

- binding 和业务参数由一个 Tool call 结构表达；
- Map 校验或 commit 失败时，业务 Tool 零 dispatch；
- 单次 Map 变更在 SQLite Store 内使用 revision CAS 原子提交；
- Map 事实与业务结果分别忠实返回。

本设计不承诺：

- SQLite 与 shell、文件系统、Git、外部 MCP 或网络服务的分布式事务；
- 普通 Tool 部分产生副作用后能够通用回滚；
- 进程在 Map commit 和业务 dispatch 之间崩溃时自动重试业务动作。

为了忠实暴露 commit/dispatch 崩溃窗口，Map Store 在同一 boundary 事务中写入最小 carrier attempt 事实：

```text
call_id, map_id, committed_revision, action, tool_name,
dispatch_status=committed_not_started|started|completed,
tool_success?, result_ref?, updated_at
```

该记录是 canonical Map action/result 事实的一部分，不是第二份 Map 或新的语义状态机：

- boundary commit 与 `committed_not_started` 在同一 SQLite 事务中写入；
- 原生 Tool dispatch 前机械更新为 `started`；
- 收到原生结果后更新为 `completed`，并记录 success/result_ref；
- 不保存 Patch 正文、shell 参数或远端 Tool 敏感 payload；
- `read_map` 必须暴露当前 node 上未完成的 attempt 摘要；当某 projection policy 本来就发出该 node 详情时，
  共享 renderer 同步带出该摘要。`map-request` 不新增主动 projection，由 Agent 通过 `read_map` 获取。

若进程在 commit 后、dispatch 前崩溃，Agent 将看到 `committed_not_started`；若在 dispatch 后、结果前崩溃，
Agent 将看到 `started` 且结果未知。Runtime 不伪造结果、不回滚 boundary、不自动重试，恢复动作仍由 Agent
决定。

## 8. 失败语义与反馈

### 8.1 统一 carrier 结果头

初始化专用 `TaskSpaceInitializationCarrierResultV1` 在实施时收敛为：

```json
{
  "schema_version": "TaskSpaceBindingCarrierResultV1",
  "action": "complete_then_continue",
  "state_commit": true,
  "tool_dispatched": true,
  "map_id": "map-...",
  "canonical_revision": 9,
  "current_node_id": "implement",
  "next_node_id": "verify"
}
```

该 JSON 头与原生 Tool result 并列：

- Function、Patch 和 code mode 使用结构上可区分的前置 content item，原正文保持原序；
- MCP 在 content 前增加独立 JSON text item，原 content 和 `is_error` 保持；
- ToolSearch 必须只生成一个 provider 配对要求的 `ToolSearchOutput(status=completed)`，再生成一个非配对
  factual `Message`；该 Message 正文携带原 `call_id` 和 carrier 状态，不得生成第二个同 call id 的 provider
  配对输出，不得把 carrier 文本塞进 `tools` 数组，也不得把 `status=completed` 误报为业务成功；
- carrier 在 dispatch 前失败时，仍生成协议要求的空配对输出，再生成唯一 carrier 失败事实。

不得把原生错误改写成 control 错误，也不得追加重试建议。B4 必须逐输出形态验证反馈顺序、原始内容和错误状态。

### 8.2 失败矩阵

| 阶段 | Map commit | Tool dispatch | 返回事实 | 后续 segment |
|---|---:|---:|---|---|
| schema/参数失败 | false | false | 一份 argument/protocol failure | 不执行 |
| stale revision/状态机失败 | false | false | 一份 canonical state failure | 不执行 |
| Store resource/CAS 失败 | false | false | 一份 Store failure | 不执行 |
| Map commit 成功、业务成功 | true | true | carrier commit + 原生成功 | 继续执行 |
| Map commit 成功、业务失败 | true | true | carrier commit + 原生失败 | 后续全部跳过 |
| commit 后、dispatch 前崩溃 | true | false | Store attempt=`committed_not_started` | 恢复后由 Agent 决定 |
| dispatch 后、结果前崩溃 | true | true/未知 | Store attempt=`started`，结果未知 | 恢复后由 Agent 决定 |

`complete_then_continue` 提交成功但后继首个业务动作失败时，前节点仍保持完成、后继节点保持 active。业务失败是
后继节点的一次真实尝试，不是前一个 boundary 的失败。

## 9. 并发、顺序与 Patch

- Store 写入继续使用 `expected_revision` CAS；冲突不 dispatch 业务 Tool。
- carrier-bound call 按 response 顺序形成 barrier，不与其他 call 并行提交。
- `active` call 继续进入现有普通并行段。
- 同一 response 最多一个 `apply_patch` 的硬门不变。
- 一个 Patch 可以携带任一合法 binding 分支，但 Patch 正文只能有一份、保持顶层原文。
- 多个 lifecycle carrier 可以连续出现，但不能借此绕过单 Patch 门。
- 任一 barrier 失败后，后续调用全部跳过；Runtime 不解释调用之间的任务语义。
- Runtime 不根据 Tool 名判断应该使用哪个 node 或 boundary。

## 10. 实施阶段

R7.1-B 获得批准后按以下顺序执行，每步独立提交并通过对应门：

### B0：schema 与成本探针

- 先生成目标 binding 与中央 control schema，不接生产执行路径。
- 验证四分支可被 DeepSeek provider profile 接受。
- 测量 Standard、当前候选和目标候选的完整 tools bytes/hash。
- 若目标超过历史 `55,578 bytes/request`，直接淘汰。
- 若目标高于当前角色分区候选 `46,926 bytes/request`，先报告增量和收益，不自动接受权衡。

### B1：统一 binding action 与 parser

- 引入 `TaskSpaceBindingAction::{Active, InitializeMap, BindNode, CompleteThenContinue}`。
- 普通 Function、Namespace、ToolSearch、延迟加载 Tool、Patch 和 code mode 共用同一投影。
- 删除 `AfterBoundary` 常量和 parser。
- 保证 Standard 不提取或删除同名普通业务字段。

### B2：扩展现有 carrier

- 将现有 initialization-only prepare/wrap 路径扩展为统一 binding carrier。
- 复用中央 lifecycle handler 的领域事务，不复制状态机逻辑。
- 在现有 Map Store 内新增最小 carrier attempt 持久化；boundary commit 与
  `committed_not_started` 必须同事务。
- 复用 ordinary Router、权限、sandbox、hook、approval 和 handler。
- 增加统一结构化日志与结果头。

### B3：删除旧双所有权

## 11. 验收矩阵

### 11.1 结构与删除

1. 普通 Tool binding 只有四个互斥对象分支。
2. `after_boundary` 在生产 schema、parser、日志、fixture 和文档当前合同中不存在。
3. 中央 control 不再暴露或解析 `bind_node`、`complete_then_continue`。
4. 旧中央非终态 payload 被确定性拒绝，且没有 fallback。
5. Agent 无法通过 provider-visible schema 表达没有普通 Tool call 的 standalone 非终态 boundary。
6. 初始化仍无法通过中央 control 表达。

### 11.2 业务参数和反馈

7. Function、MCP、ToolSearch、Patch、code mode 的业务参数剥离 binding 后精确 round-trip。
8. Patch 正文逐字节保持，单 response 多 Patch 仍零执行拒绝。
9. binding 校验失败：`state_commit=false`、`tool_dispatched=false`。
10. Map commit 成功且 Tool 失败：`state_commit=true`、`tool_dispatched=true`，原生失败只出现一次。
11. Map commit 和原生结果分别可对账，不出现重复包装或建议。
12. ToolSearch provider 配对状态与真实业务成功状态继续分离。

### 11.3 状态、并发和顺序

13. stale revision、未 ready node、错误 current binding 和 lease 冲突均零 dispatch。
14. 合法 bind + Tool 与 complete + Tool 各自一次提交、一次 dispatch。
15. 同 response 多个 carrier 按序提交；任一 barrier 或业务失败后，后续调用全部跳过。
16. `active` 普通 call 保持现有并行执行。
17. commit 后业务失败不回滚 Map，也不把 Tool failure 标成 Map failure。
18. commit 后、dispatch 前崩溃留下 `committed_not_started`；dispatch 后、结果前崩溃留下 `started`。
19. resume/fork/child 从同一 Map Store 读取 attempt，不自动重试，也不从 rollout 重建。

### 11.4 隔离、身份和成本

20. Standard 完整 Tool schema/hash/bytes 与实施前字节一致。
21. `map-always`、`map-append`、`map-request` 的 tools hash 完全一致。
22. 同一 capability epoch 内 Tool schema 不随 Map revision 或生命周期变化。
23. 目标 Tool section 不超过 `55,578 bytes/request`；高于 `46,926` 时必须单独决策。
24. Runtime 不新增自动选节点、自动补 action、自动初始化、自动重试或语义提示。
25. 17 条整体约束、现有历史回归与 R-23 Store 门全部继续通过。

### 11.5 后续模型行为门

R7.1-C 才验证以下真实模型收益，A2/B 的确定性测试不能代替：

- 两个既有 simple/complex sample，Standard + 三种 TaskSpace，repeat-3；
- standalone boundary attempts = 0；
- boundary pairing protocol reject = 0；
- 业务/协议/Map 全闭合；
- request、input、cached/uncached、output、wall、Tool bytes 和 Map 路径完整报告；
- 不增加独立初始化、事后补 Map、multi-Patch、业务失败或错误 Patch。

## 12. 日志合同

结构化 tracing 用于运行观测；第 7.4 节 carrier attempt 是 Map Store 内的 durable factual record。两者通过
`call_id + map_id + committed_revision` 对账，不能用 transient log 代替恢复事实。

| 事件 | 关键字段 | 目的 |
|---|---|---|
| `taskspace.binding_carrier.declared` | call_id、tool、action、expected_revision、node ids | 还原 Agent 声明 |
| `taskspace.binding_carrier.rejected` | call_id、action、reason_code、canonical_revision、tool_dispatched=false | 证明零 dispatch |
| `taskspace.binding_carrier.committed` | call_id、map_id、action、old/new revision、attempt_status | 对账 Store commit |
| `taskspace.binding_carrier.tool_started` | call_id、tool、map_id、revision、attempt_status | 对账 dispatch 前 durable update |
| `taskspace.binding_carrier.tool_completed` | call_id、tool、success、duration_ms、result_ref、attempt_status | 对账原生结果 |
| `taskspace.binding_carrier.sequence_skipped` | call_id、blocked_by_call_id、reason_code | 解释后续未执行 |

日志不得包含 Patch 正文、shell 敏感参数、Tool 完整结果或 API key。provider wire trace 继续只记录可审计 hash/bytes
与脱敏结构。

## 15. 参考资料与设计结论

1. [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)：strict 模式明确支持 `anyOf`；
   object 的属性需要全部列入 `required` 且 `additionalProperties=false`。因此本设计采用互斥 discriminator
   + closed object，而不依赖跨 Tool call 自然语言约束。
2. [DeepSeek Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion/)：模型可在一次响应生成一个或
   多个 Tool call，但生成参数仍必须由客户端校验。因此 Runtime 保留整响应 preflight 和 Store 硬校验。
3. [MCP Tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)：Tool 以
   `inputSchema` 定义输入，并把 Tool 执行错误作为 Tool result 交回模型。因而业务失败必须保留原始 Tool
   语义，不能被 Map carrier 改写。
4. [JSON Schema combining](https://json-schema.org/understanding-json-schema/reference/combining)：组合关键字只约束
   当前实例。它无法从一个独立 Tool 参数对象约束另一个兄弟 Tool call 必须存在，这与 R-10 的实测根因一致。
