## 1. 决策摘要

R7.1-A2 的控制对象是一次完整 provider response 中的 **Tool 类型、顺序和数量**，不是普通 Tool
本身。产品方向已经确认：

1. TaskSpace 不修改普通 Tool 的 schema、参数、描述、handler、权限、sandbox、approval、hook 或原生结果。
2. 删除普通 Tool 上的 `taskspace_binding`，不保留 `active`、`after_boundary` 或初始化 carrier。
3. `initialize_map`、`bind_node`、`complete_then_continue` 由唯一的 `taskspace_control` 表达。
4. Runtime 在任何客户端 Tool 执行前，对完整 response 的 Tool declaration manifest 做机械语法校验。
5. 初始化和非终态 boundary 后必须在同一 response 紧跟至少一个普通 Tool；终态 `finish_map` 必须是最后一个
   Tool call。
6. `taskspace_control` 是 sequence barrier。它成功提交 Map 后，后续普通 Tool 按执行时的 canonical current
   binding 归属；Runtime 不推断目标、不选择节点、不补动作。
7. 普通 Tool 是否读文件、执行命令、应用 Patch 或调用 MCP，不改变序列规则。Runtime 不检查其业务参数来判断
   “是否是有价值的后继动作”。
8. 不实现 nested all-tools dispatcher，不把 Patch 或其他 Tool 参数嵌入 control。
9. 不保留旧 wire、旧 parser、双路径或兼容 fallback。

本版本取代 v1.2 的“普通 Tool binding 承载 boundary”候选。旧方案只保留在 Git 历史中，不再是可实施方向。

## 2. 问题与根因

### 2.1 当前生产 wire

当前 TaskSpace 会把以下联合复制到每个普通 Tool：

```text
taskspace_binding.action =
  initialize_map | active | after_boundary
```

因此当前连续动作形状是：

```text
taskspace_control(complete_then_continue)
ordinary_tool(taskspace_binding=after_boundary)
```

初始化形状是：

```text
ordinary_tool(taskspace_binding=initialize_map + full graph)
```

### 2.2 侵入并未提供业务信息

`active` 只表示“使用当前 canonical binding”，而 Runtime 已从 Map Store 知道该事实。
`after_boundary` 只重复“前一个调用是 boundary”，而完整 response 的调用顺序已经包含该事实。
初始化 carrier 则为了让任意普通 Tool 都能成为首动作，把完整图 schema 复制到每个普通 Tool。

这些字段没有改变普通 Tool 能力，却造成：

- TaskSpace shared Tool schema 与 Standard 不再同形；
- 初始化图 schema 按普通 Tool 数量重复；
- freeform Patch/code mode 被投影成 Function；
- ToolSearch/MCP 等路径需要额外装饰和剥离；
- provider-native Tool 因无法携带 binding 被按 carrier 能力分类；
- sequence、router、projection 和反馈共同依赖一项本不属于普通 Tool 的协议字段。

### 2.3 直接根因

旧设计把“整个 response 是否符合 TaskSpace 工作语法”错误建模为“每个普通 Tool 必须携带 TaskSpace
生命周期参数”。这是响应级编排职责向能力层泄漏，不是多 Tool 能力不足。

Standard 和 TaskSpace 都允许一个 provider response 声明多个 Tool call。当前 sequence runner 也已经能够：

- 收集完整 response 的 Tool declaration；
- 在执行前做 response-wide preflight；
- 把 control 与 Patch 作为 barrier；
- 并行执行无结果依赖的普通 Tool；
- 在前置 barrier 失败后跳过依赖调用。

因此正确抽象是 response grammar，而不是 ordinary Tool decoration。

## 3. 目标与非目标

### 3.1 目标

- shared ordinary Tool 在 Standard 与 TaskSpace 中 provider-visible schema 字节一致。
- TaskSpace 连续动作由 response 中的 Tool 类别、位置和计数确定。
- 空 Map 不能先执行普通 Tool；初始化不能作为成功的单独 request。
- 非终态 boundary 不能作为成功的单独 request。
- 同一 response 可表达多个 boundary + ordinary Tool 段。
- 普通 Tool 在实际 dispatch 时读取最新 canonical binding。
- preflight、Map commit、普通 Tool dispatch 和原生结果可独立观测。
- 三种 projection policy 使用同一个序列合同和执行器。

### 3.2 非目标

- 不从普通 Tool 名称、命令、查询、路径、Patch 内容或结果判断任务语义。
- 不保证 Agent 选择的普通 Tool 在业务上正确或有价值。
- 不让 Runtime 自动初始化、选择节点、创建图、重试或修复参数。
- 不把整次 response 做成跨 SQLite、文件系统、进程和远端 MCP 的分布式事务。
- 不改变“有结果依赖的后续动作必须等待下一次 provider response”的模型循环事实。
- 不在 A2 同时解决 R-22 的 multi-Patch 生成倾向或 projection 策略收益。

## 4. 响应级 Tool 类型

序列合同只分类 Tool declaration，不读取普通 Tool 业务参数：

| 记号 | 类型 | 包含 | 序列作用 |
|---|---|---|---|
| `I` | Initialization control | `taskspace_control.initialize_map` | 创建 canonical Map；barrier |
| `B` | Nonterminal boundary | `bind_node`、`complete_then_continue` | 改变 current binding；barrier |
| `C` | Independent Map control | graph mutation、block/unblock/rework、read/expand | 按自身合同执行；barrier |
| `T` | Terminal control | `finish_map` | 显式闭合 Root/Finish；终态 barrier |
| `O` | Ordinary Tool | exec、read、MCP、ToolSearch、Patch 等可进入客户端序列的 Tool | 原生执行 |
| `P` | Patch subtype | `apply_patch`，同时属于 `O` | 每 response 最多一个 |
| `U` | Unsequenceable provider-native capability | 完整 manifest 前已在 provider 侧执行的 Tool | 不能充当 `I/B` 后继 |

`O` 的分类只回答“它是否是一个可由客户端 sequence runner 调度的普通 Tool”，不回答它做什么。

## 5. 正式序列语法

### 5.1 分段语法

对完整 response 中按声明顺序排列的客户端 Tool calls，定义：

```text
Response        := Segment+
Segment         := InitSegment
                 | BoundarySegment
                 | OrdinarySegment
                 | ControlSegment
                 | TerminalSegment

InitSegment     := I O+
BoundarySegment := B O+
OrdinarySegment := O+
ControlSegment  := C
TerminalSegment := T
```

`O+` 在下一个 control 或 response 结束前持续。多个段可在同一 response 中组合：

```text
I O O
B O
B O O
C
B P O
T
```

### 5.2 数量规则

1. 空 Map 上必须恰有一个 `I`，且它必须是第一个客户端 Tool call。
2. 已初始化 Map 上 `I` 数量必须为零。
3. 每个 `I` 后至少有一个 `O`。
4. 每个 `B` 后至少有一个 `O`。
5. `T` 每个 response 最多一个，且必须是最后一个 Tool call。
6. `P` 每个 response 最多一个。
7. `O` 不设置人为总量上限；只受 provider、上下文和通用执行预算约束。
8. 一个 response 可以有多个 `B O+` 段，不限制合法 boundary 数量。

### 5.3 顺序规则

合法：

```text
I, O
I, O, O
O, O
B, O
O, B, O, O
B, O, B, O
B, P, O
T
```

非法：

```text
O, I
I
B
B, C
T, O
T, B, O
P, P
```

`C` 不满足 `I/B` 的真实动作要求，因为它仍是 Map control，不是业务 Tool。`T` 是唯一允许不携带后继普通
Tool 的生命周期闭合动作。

### 5.4 消息与 reasoning

语法只作用于 provider 返回的 Tool declaration 顺序，不解析 reasoning，不扫描自然语言消息，也不根据
assistant 文本推断缺失动作。Tool calls 之外的内容不参与序列配对。

## 6. L4 Tool 合同

### 6.1 普通 Tool

TaskSpace 对 shared ordinary Tool 做零 schema 装饰：

```text
TaskSpace ordinary Tool schema == Standard ordinary Tool schema
```

不得新增：

```text
taskspace_binding
taskspace_action
taskspace_transition
next_tool
next_tool_arguments
```

原生 freeform `apply_patch` 和 code mode 不再为了 TaskSpace 转成 Function。ToolSearch 返回的延迟 Tool 也不做
TaskSpace 参数投影。

### 6.2 taskspace_control

中央 control 是唯一 Agent 可见 Map 操作 Tool，保留：

```text
initialize_map
bind_node
complete_then_continue
mutate_graph
block_node
unblock_node
rework_node
finish_map
expand_nodes
read_map
read_output_ref
```

它的 schema 只约束自身 action 和 Map 参数。Tool 描述应准确声明 `I/B/T` 的 response 序列规则，但不嵌入普通
Tool schema，也不列举业务命令范例。

### 6.3 为什么允许 response preflight

JSON Schema 只能约束当前 Tool 参数对象，不能约束 provider response 中另一个 sibling Tool call。当前 provider
协议也不允许客户端为整个 `tool_calls[]` 提供一个外层 JSON Schema。

因此 response grammar 由 Runtime 在完整 response 生成后、任何客户端 Tool 执行前验证。这是状态机硬规则的
机械准入，不是执行后的语义惩罚：

- 不读取普通 Tool 业务内容；
- 不修改 Agent 声明；
- 不生成替代动作；
- 不执行一部分非法 response；
- 返回实际类别序列、失败索引和违反的数量/顺序规则。

## 7. L5 执行语义

### 7.1 完整响应 preflight

Runtime 先构造不可变 manifest：

```json
{
  "response_id": "...",
  "map_state": "blank | active | terminal",
  "calls": [
    {"index": 0, "class": "B", "tool": "taskspace_control"},
    {"index": 1, "class": "O", "tool": "exec_command"}
  ],
  "counts": {
    "initialization": 0,
    "boundary": 1,
    "terminal": 0,
    "ordinary": 1,
    "patch": 0
  }
}
```

manifest 不复制普通 Tool arguments。preflight 只检查：

- response 是否完整；
- Tool declaration 是否可解析；
- `I/B/C/T/O/P/U` 分类；
- 第 5 节的数量和顺序；
- 当前 Map 状态允许的 control 类型；
- response-wide 单 Patch。

语法失败时所有客户端调用均零 dispatch、Map 零 commit。

### 7.2 Barrier 与 canonical binding

合法 response 按 manifest 顺序分段执行：

1. `I/B/C/T` 独占执行并从 Map Store 读取 canonical revision。
2. control 参数通过硬规则后以 Store CAS 提交。
3. control 后的 `O` 在 dispatch 时读取提交后的 canonical current binding。
4. 相邻 `O` 若原生 Tool 支持并行，则继续使用共享 parallel scheduler。
5. 下一个 control 等待前一个 ordinary segment 完成后再执行。

“dispatch 时读取 current binding”是状态读取，不是 Runtime 替 Agent 选择节点。节点选择已经由前面的
`initialize_map`、`bind_node` 或 `complete_then_continue` 明确提交。

### 7.3 失败语义

| 失败位置 | Map | 普通 Tool | 后续调用 | Agent 可见事实 |
|---|---|---|---|---|
| response grammar | 零提交 | 零执行 | 全部不执行 | 一份 sequence preflight failure |
| control schema/硬规则 | 失败 control 零提交 | 其后依赖段不执行 | 标记 skipped | 原 control failure + skip facts |
| Store CAS | 零提交 | 其后依赖段不执行 | 标记 skipped | revision/conflict 原因 |
| 普通 Tool | 已提交 boundary 不回滚 | 原生失败 | 沿用通用 sequence 失败规则 | Map commit fact + 原生 Tool result |
| 进程在 commit 后崩溃 | commit 保留 | attempt 可能未开始或未完成 | 不自动重试 | Store attempt/audit fact |

Runtime 不把业务失败改写成 Map 失败，也不因为业务 Tool 失败回滚一个已经合法提交的 Agent lifecycle 决定。

## 8. Provider-native 能力边界

部分 provider-native Tool 可能在客户端收到完整 response 前已经由 provider 执行，无法满足“preflight 失败时
零业务执行”。A2 不通过修改这些 Tool schema 来伪造可序列化能力。

R7.1-B0 必须逐类确认：

1. declaration 是否在执行前对客户端可见；
2. 是否能进入统一 manifest；
3. 是否能由 sequence barrier 排序；
4. 是否能返回原生结果和失败。

不能满足四项的能力分类为 `U`，不得充当 `I/B` 后继。是否在 TaskSpace 整体隐藏、只允许 active Map 使用，
或由 provider adapter 提供真正的客户端执行形态，是独立产品能力决策；B0 发现该情况时必须暂停，不得静默隐藏、
自动降级或重新给普通 Tool 增加 carrier。

## 9. 五层职责

| 层 | 本方案职责 | 禁止 |
|---|---|---|
| L1 | Map 价值、Agent/Runtime 宏观边界 | Tool 序列枚举和 JSON |
| L2 | 说明 `I O+`、`B O+`、`T` 的日常工作循环和恢复 | 复制所有 control 参数 |
| L3 | 复杂 DAG、长任务和重规划经验 | 成为序列正确性的前提 |
| L4 | `taskspace_control` action schema；普通 Tool 保持原生 | 普通 Tool TaskSpace 装饰 |
| L5 | manifest、preflight、barrier、Store commit、事实反馈 | 读取业务参数推断动作意义 |

## 10. 迁移范围

生产实施必须一次性完成：

1. 从 provider Tool projection 删除普通 Tool `taskspace_binding` 装饰。
2. 恢复 Function、Namespace、ToolSearch、MCP、Patch 和 code mode 原生 schema。
3. 从 Router/ToolCall 删除 binding 提取、剥离和验证。
4. 从普通 Tool 执行路径删除 initialization carrier。
5. 将 `initialize_map` 恢复为中央 `taskspace_control` action。
6. 保留 `bind_node`、`complete_then_continue` 在中央 control。
7. 删除 `after_boundary` 常量、parser、manifest 字段和反馈。
8. sequence manifest 改为响应级类型分类与计数。
9. preflight 改为第 5 节语法，不保留旧 carrier fallback。
10. observer 从 binding 指标迁移到 segment/grammar 指标。
11. 同步 L2 中旧 wire 说明，不修改 L1 或 L3。

## 12. 分阶段实施

### R7.1-B0：能力与成本探针

**Entry:** 本文和整体约束完成同步。

**Tasks:**

- 盘点所有 ToolSpec 形态是否能进入完整 response manifest；
- 证明 shared ordinary Tool 在零装饰候选下与 Standard schema byte-identical；
- 测量 `Standard tools + taskspace_control` 的固定 bytes；
- 对 `U` 能力形成明确清单和产品决策点；
- 冻结旧版、候选版 schema/manifest golden。

**Exit:** 无未知 Tool 形态；若存在 `U`，暂停等待产品决策；不依赖 B1 证据。

### R7.1-B1：纯序列分类器与 preflight

**Tasks:**

- 实现 typed `I/B/C/T/O/P/U` manifest；
- 实现第 5 节有限状态语法；
- 覆盖合法多段、非法顺序、数量、空/active/terminal Map 状态；
- 证明 preflight 不读取普通 Tool arguments。

**Exit:** 正负 fixture 全通过，非法 response 零执行；尚不切生产 provider 路径。

### R7.1-B2：L4 wire 原子迁移

**Tasks:**

- 删除普通 Tool decoration 和 binding parser；
- 恢复中央初始化；
- 恢复原生 Patch/code mode/ToolSearch/MCP schema；
- 更新 L2、Tool 描述、observer schema；
- 删除旧 wire 测试和兼容入口。

**Exit:** Standard/TaskSpace shared Tool golden 字节一致；源码扫描无旧 binding；编译与 schema 测试通过。

### R7.1-B3：生产 sequence 与 Store 接线

**Tasks:**

- 在完整 response 后、任何执行前接入 B1 preflight；
- 按 barrier 顺序执行 control 与 ordinary segments；
- dispatch 时读取 canonical binding；
- 接入失败、skip、commit 和 result 事实。

**Exit:** initialize + action、多个 boundary + action、control + Patch、失败矩阵生产集成测试通过。

### R7.1-B4：观测与残留门

**Tasks:**

- observer 改为 segment、order、count、barrier 和 dispatch 指标；
- 删除 binding 特有指标或明确标记为 historical artifact；
- 增加 Standard 隔离、provider wire、Map attribution 和敏感信息测试；
- 扫描无 decoration、旧 parser、carrier executor 和兼容分支。

**Exit:** 日志链可对账；所有残留门通过；不依赖真实模型统计。

### R7.1-B5：整体工程准入

**Tasks:**

- 运行五层合同、TaskSpace、Patch、ToolSearch/MCP、Map Store、subagent、resume/fork 回归；
- 构建 Whale CLI 和 Docker benchmark image；
- 对比 fixed Tool bytes、schema hash 和 cache prefix；
- 执行 fresh-context 对抗性审查。

**Exit:** 工程门全部通过且无未决 High finding，才允许进入 R7.1-C repeat-3。

## 15. 验收标准

### 15.1 结构

1. 所有 shared ordinary Tool 在 Standard/TaskSpace 中 schema byte-identical。
2. TaskSpace ordinary Tool schema 中 `taskspace_binding` 出现次数为零。
3. `initialize_map`、`bind_node`、`complete_then_continue` 只存在于 `taskspace_control`。
4. Patch/code mode 保持原生 freeform。
5. 三种 projection policy 的 Tool hash 完全一致。

### 15.2 行为

1. 空 Map 首 response 成功路径为 `I O+`。
2. `I`、`B` 单独 response 均零执行拒绝。
3. `B O+ B O+` 在一个 response 按 barrier 顺序完成。
4. `T` 后任何 Tool 都零执行拒绝。
5. 多普通 Tool和单 Patch能力不回退。
6. 普通 Tool 失败保留原始反馈，不改写 Map 事实。
7. Runtime 从不检查普通 Tool 业务参数判断序列合法性。

### 15.3 成本

1. shared ordinary Tool 固定 bytes 与 Standard 相同。
2. TaskSpace 额外 Tool schema 只来自唯一 `taskspace_control` 和明确的可见 Tool 集差异。
3. 总 Tool section 必须低于当前 `46,926 bytes/request` 候选；同时报告首请求、累计 Input、cache 和 wall。
4. 成本收益不能抵消行为、Patch、Map 或反馈回归。

## 16. 风险与回退

| 风险 | 触发证据 | 缓解 | 回退 |
|---|---|---|---|
| Agent 仍生成单独 boundary | live trace 中 grammar reject | L2/L4 准确描述；不增加普通 Tool carrier | 回退整个 B 候选 |
| sequence parser 与执行顺序不一致 | manifest/dispatch index 不一致 | 同一 typed manifest 驱动两者 | 回退整个 B 候选 |
| provider-native Tool 绕过 preflight | B0 出现 `U` | 暂停产品决策，不静默放行 | 不进入 B1 |
| binding 归属读取旧 revision | node/revision trace mismatch | dispatch 时 Store read + lease gate | 回退整个 B 候选 |
| 普通 Tool schema 未完全恢复 | Standard/TaskSpace golden diff | 残留扫描和 wire hash | 回退整个 B 候选 |
| Patch 形态回归 | freeform/golden 失败 | Patch 专项门 | 回退整个 B 候选 |

不允许只恢复 `taskspace_binding` 作为临时 fallback。若候选失败，回退整个候选提交，生产继续使用前一基线。

## 17. 替代方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 每个普通 Tool 携带 lifecycle union | 淘汰 | 响应编排侵入能力层，固定成本按 Tool 数量复制 |
| 普通 Tool 只携带 active/after_boundary | 淘汰 | 两个字段均可由 canonical state 和顺序机械确定 |
| 普通 Tool carrier 承载 boundary | 淘汰 | 虽能使单 call 不可分离，但继续污染所有普通 Tool |
| nested all-tools dispatcher | 淘汰 | 参数嵌套、Patch 转义、权限和 handler 平行架构 |
| Runtime 自动推断节点或 next action | 淘汰 | 越过状态机底线并替 Agent 决策 |
| 只写提示词、不做 preflight | 淘汰 | 无法保障状态机硬顺序 |
| response grammar + 原生 ordinary Tools | 采用 | 控制对象与实际问题一致，复用现有多 Tool 和 barrier |

## 18. 外部依据

1. [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)：一次模型响应可以生成一个或多个
   Tool call，客户端仍需验证参数和执行边界。
2. [DeepSeek Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion/)：并行 Tool call 是
   provider response 能力，不要求把编排参数复制到每个 Tool。
3. [MCP Tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)：Tool 的
   `inputSchema` 描述该 Tool 自身输入，执行错误通过 Tool result 返回。
4. [JSON Schema combining](https://json-schema.org/understanding-json-schema/reference/combining)：组合关键字约束
   当前 JSON 实例，不能约束 provider response 中另一个 sibling Tool call。
