## 1. 决策摘要

R7.1-A2 控制的是一次完整 provider response 中的 TaskSpace 动作声明、普通 Tool 数量和两者的机械对应关系。
它不修改普通 Tool，也不替 Agent 选择工作节点。

目标模型只有一套：

1. Map 是独立持久化、全局唯一的有向依赖图，也是 TaskSpace 状态机本身。
2. Root 是唯一起点，Finish 是唯一终点；除 Root 外每个节点至少有一个入边，允许多父依赖。
3. Agent 为每个普通 Tool call 显式声明 `node_id`。一个 response 可以推进多个不同节点。
4. 不存在 canonical `current_node`、`current_binding`、`next_node` 或 singleton main lease。
5. 普通 Tool schema、参数、handler、权限、sandbox、approval、hook 和原生结果完全不知道 `node_id`。
6. `taskspace_control` 提供 response 级 action manifest；Runtime 只按顺序和名称将 manifest 与 sibling 普通
   Tool calls 一一对应。
7. 非终态 Map 变更不能单独成功，必须和至少一个真实普通动作位于同一 response。
8. `read_map`、`read_output_ref` 可在确实存在结果依赖时单独调用；`finish_map` 是唯一允许单独出现的终态动作。
9. Runtime 在任何普通 Tool dispatch 前完成全响应机械校验；失败时零普通 Tool 执行、零 Map commit。
10. 不持久化 `Open`。`Waiting`、`Ready`、`InFlight`、`Blocked`、`Completed` 都由事实计算。
11. Map 生命周期只有 `不存在 -> 进行中 -> 已关闭` 及用户反馈后的 `已关闭 -> 进行中`；分别由
    `initialize_and_execute`、`finish_map` 和 `reopen_map` 表达。
12. `finish_map` 同时完成 Agent 明确列出的最后 Work、关闭 Finish 与 Root 并提交总结，避免最后 Work 无法合法
    闭合；`reopen_map` 恢复同一个 Task Map，但不反转任何已完成 Work。

本版本完整取代 v2.0 的 `bind_node + canonical current binding + I/B/C/T/O` 设计。旧 wire、旧 parser、双路径
和行为兼容分支均不保留。

## 2. 为什么必须重写

### 2.1 旧方案错误地假设只有一个当前节点

v2.0 以如下链路归属普通动作：

```text
bind_node(node-A)
ordinary_tool() -> Runtime 从 current binding 推导 node-A
complete_then_continue(node-A, node-B)
ordinary_tool() -> Runtime 从 current binding 推导 node-B
```

这与真实 Map 模型冲突：

- 多个未闭合子节点可同时 `Ready` 或 `InFlight`；
- 同一 response 可在不同节点执行互不依赖的动作；
- 多父依赖图不存在天然的单一“下一节点”；
- Agent 才是动作归属的声明者，Runtime 无权推断或选择；
- singleton binding 把有向图退化为一条 Runtime 驱动的游标。

### 2.2 `Open` 重复表达已有事实

`Open` 只是“尚未完成”的宽泛集合。它与依赖、阻塞、执行中和完成事实重叠，容易出现两份状态不一致：

```text
Open = Waiting ∪ Ready ∪ InFlight ∪ Blocked
```

因此 `Open` 只能作为查询或指标的派生概念，不能作为节点的持久化状态或转换目标。Work completion 只记录
Work；Root 与 Finish 是否关闭只由当前 `terminal_record` 派生，不需要额外保存 `Open` 或重复 completion。

### 2.3 Tool 归属不属于普通 Tool 能力

`exec_command`、`read_file`、`apply_patch`、MCP Tool 等普通能力不需要理解 TaskSpace。把 `node_id`、
`taskspace_binding` 或 lifecycle union 塞进这些 Tool 会：

- 破坏 Standard 与 TaskSpace 的 shared Tool 同形；
- 放大固定 schema 和 input token；
- 改变 freeform Patch/code mode；
- 迫使 ToolSearch、MCP 和 provider-native 能力建立专用分支；
- 让普通 Tool handler 承担 Map 编排职责。

动作归属必须存在，但应位于 TaskSpace 外层调用上下文，而不是普通 Tool 参数。

## 3. Canonical Map 与状态模型

### 3.1 图结构硬不变量

Map 必须满足：

1. 恰有一个 Root，且它是唯一入度为零的节点。
2. 恰有一个 Finish，且它是唯一出度为零的终态节点。
3. 除 Root 外每个节点至少有一个入边。
4. 所有节点从 Root 可达。
5. 所有非 Finish 节点存在到 Finish 的路径。
6. 图无环；一个节点可有多个前置节点和多个后继节点。
7. Agent 创建节点、边和动作归属；Runtime 只验证这些机械不变量。
8. Root 只在 Agent 显式 `finish_map` 时与 Finish 一起闭合，不自动触发。

### 3.2 持久化事实

Map Store 保存事实，不保存互相重叠的状态标签：

```text
Map:
  map_id
  revision
  root_node_id
  finish_node_id
  nodes
  edges
  completion_records
  block_records
  action_reservations
  results_and_evidence
  terminal_record
  terminal_history
```

节点机械角色必须由结构表达：

```text
root
work_nodes[]
finish
edges[]
```

不得恢复单数 `initial_work_node`，也不得把 Root、Work、Finish 压成通用 `nodes[] + role_id` 后依赖描述文字维持
互斥。初始化时可以存在多个首批 Ready work nodes。

### 3.3 派生视图

以下状态均由 Store 事实计算，不单独成为第二事实源：

| 视图 | 计算条件 |
|---|---|
| Work `Completed` | 存在有效 Work completion record |
| Root / Finish `Completed` | 存在当前有效 `terminal_record` |
| `Blocked` | 未完成且存在有效 block record |
| `InFlight` | 未完成且存在未释放的 action reservation |
| `Ready` | 未完成、未阻塞、前置条件满足，且机械并发条件允许 |
| `Waiting` | 未完成、未阻塞，但前置条件尚未满足 |

如日志需要 `open_nodes`，其值只能由上述事实即时计算，不能写回 Store：

```text
open_nodes = Waiting ∪ Ready ∪ InFlight ∪ Blocked
```

### 3.4 Map 生命周期

Map 级生命周期与节点派生状态是两个不同概念。节点不持久化 `Open`；整个 Map 则有三个产品状态：

| 当前状态 | Agent 动作 | 下一状态 | 产品含义 |
|---|---|---|---|
| 不存在 | `initialize_and_execute` | 进行中 | 创建当前 Task Map 并立即执行首批工作 |
| 进行中 | `finish_map` | 已关闭 | 完成最后 Work，关闭唯一 Finish 与 Root，提交精确总结 |
| 已关闭 | `reopen_map` | 进行中 | 用户后续反馈表明同一任务仍需工作，恢复当前 Task Map 并立即继续 |

`reopen_map` 是唯一的“已关闭 -> 进行中”动作，不是唯一的 Map 级生命周期动作；`finish_map` 是与之相对的
“进行中 -> 已关闭”动作，`initialize_and_execute` 则创建 Map 并进入进行中。

关闭主动权属于 Agent。`finish_map` 成功后当前 turn 立即结束，因此不存在 Agent 在没有新用户消息时自行
`reopen_map` 的执行机会。新用户消息到来后，Agent 判断它是同一任务的补充工作、仅需回答的问题，还是其他任务：

- 同一任务仍需实际工作：调用 `reopen_map`；
- 只需解释已有结果：直接回答，不改变 Map；
- 无关的新任务：不得把它伪装为当前 Map 的补充工作，另行进入新任务生命周期。

Runtime 不解析用户反馈文本，也不判断任务是否真的未完成。它只验证 `reopen_map` 的当前状态、revision、候选图、
action manifest 和原子提交条件。

每次关闭都是真实历史，不得被 reopen 覆盖或删除：

```text
terminal_record:
  当前有效的关闭记录；进行中时为空

terminal_history[]:
  历次被后续用户反馈重新打开的关闭记录
```

`reopen_map` 原子地把当前 `terminal_record` 移入 `terminal_history[]`；Root/Finish 因当前 terminal 为空而恢复
进行中派生视图。随后同一事务新增后续 Work 和依赖，并为同 response 的真实动作建立 reservation。这里不新增
持久化 `Open` 字段，也不删除任何 Work completion。

节点级 `rework_node` 被删除。既有 completion、result 和 evidence 都是已经发生的事实，不能因为用户反馈而倒退。
新反馈暴露出的遗漏、修正或补充工作一律由 Agent 新增 Work 节点表达。

## 4. Agent 可见 Tool 合同

### 4.1 普通 Tool 零侵入

硬等式：

```text
TaskSpace shared ordinary Tool schema == Standard shared ordinary Tool schema
TaskSpace native ToolCall == Standard native ToolCall
```

普通 Tool 不得新增：

```text
node_id
taskspace_binding
taskspace_action
taskspace_transition
next_tool
next_tool_arguments
```

### 4.2 为什么使用 action manifest

DeepSeek 原生 Tool Call 只有 `id`、`name` 和 `arguments`，没有可由 Agent 写入的独立 metadata。为保持普通 Tool
原生形状，Agent 在同一 response 的 `taskspace_control` 中声明有序 action manifest，普通 Tool 仍作为原生
sibling calls 存在：

```text
taskspace_control({
  "action": "execute",
  "expected_revision": 12,
  "mutations": [
    {"action": "complete_node", "node_id": "inspect"}
  ],
  "actions": [
    {"node_id": "implement", "tool": "apply_patch"},
    {"node_id": "verify", "tool": "exec_command"}
  ]
})
apply_patch(...)
exec_command(...)
```

`actions[]` 不嵌入、不复制普通 Tool 参数。它只声明 sibling call 的节点归属和 Tool 名称。Runtime 按响应顺序
校验：

```text
actions[0] <-> sibling ordinary_tool[0]
actions[1] <-> sibling ordinary_tool[1]
```

这不是 nested dispatcher。普通 Tool 仍由原生 router、handler、权限与 sandbox 执行。

### 4.3 taskspace_control 的六种顶层 action

```text
initialize_and_execute
execute
reopen_map
read_map
read_output_ref
finish_map
```

#### initialize_and_execute

用于空 Map 的第一次有效工作：

```json
{
  "action": "initialize_and_execute",
  "root": {"node_id": "root", "goal": "..."},
  "work_nodes": [
    {"node_id": "inspect", "goal": "..."},
    {"node_id": "research", "goal": "..."}
  ],
  "finish": {"node_id": "finish", "goal": "..."},
  "edges": [
    {"from": "root", "to": "inspect"},
    {"from": "root", "to": "research"},
    {"from": "inspect", "to": "finish"},
    {"from": "research", "to": "finish"}
  ],
  "actions": [
    {"node_id": "inspect", "tool": "read_file"},
    {"node_id": "research", "tool": "exec_command"}
  ]
}
```

它必须有 `actions+` 和等量原生 sibling Tool calls。初始化不能占用一个单独 provider request。

#### execute

用于已初始化 Map 的所有非终态推进：

```text
execute:
  expected_revision
  mutations[]
  actions[1..]
```

`mutations[]` 可表达：

- `add_work_nodes`
- `add_edges`
- `remove_edges`
- `complete_node`
- `block_node`
- `unblock_node`

创建、补边、完成和阻塞变更均不能单独成功。Agent 必须同时声明至少一个真实动作；动作可属于不同节点，也可
属于本次 mutation 新增且在候选图中已 Ready 的节点。

#### reopen_map

只用于用户反馈后的同一 Task Map 继续工作：

```json
{
  "action": "reopen_map",
  "expected_revision": 18,
  "work_nodes": [
    {"node_id": "address-feedback", "goal": "完成用户指出的遗漏工作"}
  ],
  "edges": [
    {"from": "root", "to": "address-feedback"},
    {"from": "address-feedback", "to": "finish"}
  ],
  "actions": [
    {"node_id": "address-feedback", "tool": "exec_command"}
  ]
}
```

它必须满足：

1. 当前 Map 已关闭；
2. `work_nodes[]`、`edges[]` 和 `actions[]` 均非空；
3. 新 Work 仍处于同一 Root 到唯一 Finish 的合法 DAG；
4. 每个 action 与同 response 的普通 sibling Tool 一一对应；
5. reopen、图变更和 action reservations 在一个事务中提交；
6. 不允许单独 reopen，也不允许修改或删除历史 completion。

#### read_map / read_output_ref

只有当后续动作确实依赖读取结果时，才允许单独响应。它们是事实读取，不改变 Map，不暗示下一步。

#### finish_map

唯一终态 action：

```text
finish_map:
  expected_revision
  finish_node_id
  complete_work_node_ids[1..]
  exact_summary
```

`complete_work_node_ids[]` 是 Agent 对最后一批 Work 的明确完成声明。Runtime 在同一事务中依次验证并写入这些
completion，然后验证唯一 Finish 已 Ready、无 InFlight reservation 和图闭合条件，最后关闭 Finish 与 Root 并
原样保留 `exact_summary`。Runtime 不根据 Tool 成功、测试结果或任务内容自动选择完成节点。

这个终态合同解决了旧设计的不可达问题：若 `execute` 强制携带下一动作，而 `finish_map` 又要求所有 Work 事先
完成，最后一个 Work 永远无法在有限请求内合法闭合。正确产品节奏是：

```text
中途：complete current Work + next actions
最后：complete final Work + finish Map + exact summary
```

## 5. 合法响应形状

TaskSpace 客户端 Tool response 只允许：

```text
INITIALIZE_AND_EXECUTE(actions+) + matching ordinary sibling Tool calls
EXECUTE(mutations*, actions+) + matching ordinary sibling Tool calls
REOPEN_MAP(work_nodes+, edges+, actions+) + matching ordinary sibling Tool calls
READ_MAP
READ_OUTPUT_REF
FINISH_MAP
```

明确非法：

```text
ordinary_tool without action manifest
initialize without ordinary action
standalone graph mutation
standalone complete_node
standalone block
standalone reopen_map
rework_node
bind_node
complete_then_continue
next_node
current_node
finish_map followed by ordinary Tool
multiple taskspace_control calls in one response
multiple Patch calls in one response
```

不再存在泛化的 standalone `C`。非终态 control-only response 会造成空转和请求放大，因此不是合法产品能力。

## 6. Runtime 外层调用模型

### 6.1 内部 envelope

Runtime 依据 Agent manifest 构造外层执行对象：

```text
ActionMapPreparedCall:
  map_id
  expected_revision
  node_id
  response_call_index
  native_tool_call
  reservation_id
```

`node_id` 的唯一来源是 Agent 的 `actions[]`。Runtime 不能：

- 从 current node 推断；
- 缺失时使用默认节点；
- 根据 Tool 名称、参数、路径或结果选择节点；
- 把某个 Ready 节点提升为当前节点；
- 自动生成 action manifest；
- 在 manifest 不匹配时修复或重排普通 Tool。

原生 handler 只收到 `native_tool_call`，不会看到外层字段。

### 6.2 全响应 preflight

任何客户端普通 Tool 执行前，Runtime 一次性检查：

1. response 已完整结束，不是 partial/interrupted manifest；
2. 恰有一个 `taskspace_control`，且位置和 action 合法；
3. `actions.len == ordinary_sibling_calls.len`；
4. 每个 `actions[i].tool == ordinary_sibling_calls[i].name`；
5. 每个 action 都有 Agent 显式声明的 `node_id`；
6. 不存在额外或缺失的普通 Tool call；
7. node 存在、未完成、处于派生 Ready，revision 有效；
8. mutations 后的候选图满足 DAG、Root、Finish、可达性和角色约束；
9. 每个 action 的 reservation 可原子建立；
10. 每个 response 最多一个 Patch；
11. `reopen_map` 仅接受已关闭 Map，且新增 Work、edges、actions 与 sibling calls 完整匹配；
12. `finish_map` 无 sibling calls，显式完成的最后 Work 能使唯一 Finish Ready，并满足终态硬门。

Runtime 不读取普通 Tool 业务参数来判断动作是否合理，也不解析 reasoning 或 assistant 文本补全合同。

### 6.3 提交与执行顺序

合法非终态 response 的机械顺序：

```text
collect complete response
-> preflight manifest and candidate Map
-> one Store transaction:
     apply mutations
     create per-action reservations
     increment revision
-> dispatch native sibling Tools through existing runner
-> attribute each raw result to its declared node
-> release reservation and persist factual result
```

preflight 失败：零普通 Tool dispatch、零 Map commit。普通 Tool 失败不回滚已提交的 Map mutation，也不自动完成、
阻塞、重试或重规划节点；Agent 在下一 response 基于原始事实决定如何处理。

### 6.4 多动作、并行与结果依赖

- 无结果依赖的普通动作可以在同一 response 声明并由现有 runner 并行执行。
- Patch 继续是 barrier，且每 response 最多一个。
- 如果动作 B 的参数取决于动作 A 的结果，Agent 必须等待结果后在下一 provider response 声明 B。
- Runtime 只执行 Agent 已声明的顺序和依赖事实，不创造并行或串行策略。

## 7. 反馈与 projection

Agent 可见 control result 只报告事实：

```text
accepted
map_id
revision_before
revision_after
committed_mutations
reserved_actions[{call_index,node_id,tool,reservation_id}]
rejected_reason
```

普通 Tool result 保持原始语义，仅附加独立的 TaskSpace attribution envelope；不得把结果改写成 lifecycle 建议。

projection 展示全局图和派生状态，但不得显示不存在的 `current_node` 或持久化 `Open`。近端细节、证据折叠和三种
projection policy 继续遵循既有 L5 设计，本 A2 不改变其语义。

## 8. 生产残留与影响面

当前实现仍广泛依赖旧模型，不能把 A2 当作单文件 Tool schema 修改：

| 模块 | 现有残留 | 目标 |
|---|---|---|
| rooted DAG model | `NodeStatus::Open`、`current_binding` | 事实型生命周期与派生视图 |
| Runtime | `current_node_id`、`current_main_node_id/main_lease` | per-action reservation，无 singleton pointer |
| initialization | 单数 `current_work_node` / `initial_work_node` | `work_nodes[]` 与多首批 Ready |
| transitions | `Bind`、`CompleteHandoff`、Ready -> Running 游标 | mutations + Agent action manifest |
| projection | 固定输出 `current_node` | 全图、派生状态、无当前节点 |
| Tool schema/parser | `bind_node`、`complete_then_continue` | 六个顶层 action |
| sequence preflight | `active/after_boundary` 配对 | manifest 与 sibling calls 逐项配对 |
| event/result | 事件 owner 接受 `current_node_id` | 接受显式 action attribution |
| subagent | main lease/current binding 一致性 | 共享 Store Map + node/action reservation |
| tests/fixtures | Open/current binding 为默认前提 | rooted DAG、多 Ready、多节点同 response |

残留审计已在生产与测试路径中定位至少 36 个相关文件。实施必须按模块迁移并设置残留门，不能只删 Agent 可见字段。

## 9. 重写后的实施计划

旧 A2 v2.0 的 B0-B5 计划作废。2026-07-27 的生产依赖审计又确认：旧 v3.0 将 B1 domain/Store、
B2 schema/parser、B3 preflight 和 B4 execution attribution 分成了不能独立成立的阶段。当前普通 Tool
不声明 `node_id`，旧 Runtime 只能通过 singleton current/main lease 归属结果；若先单独删除 current，
Tool 结果将失去节点身份。用隐藏游标跨越 B1-B3 只是恢复被否决的设计。

## 11. 完成定义

A2 只有同时满足以下条件才算完成：

1. 生产代码不再存在 singleton current-node/binding 语义。
2. `Open` 不再是持久化 canonical 状态。
3. Agent 对每个普通动作显式声明 `node_id`。
4. Runtime 不推断、选择、默认或修复动作归属。
5. 普通 Tool 在 Standard 与 TaskSpace 中 schema、参数和 handler 原生同形。
6. 非终态 Map 操作和真实动作同 response，且不产生稳定额外请求。
7. preflight 失败零普通 Tool dispatch、零 Map commit。
8. 多 Ready、多 InFlight、多父依赖和多节点同 response 均有测试。
9. 三种 projection policy 共用同一 Map、Tool、Runtime、反馈和状态机。
10. 最后 Work 可由 Agent 在 `finish_map` 原子完成，不存在终态不可达循环。
11. 用户反馈后可通过 `reopen_map + 新 Work + actions` 继续同一 Map，历史完成事实不倒退。
12. 生产 schema、parser、domain 和文档不存在 `rework_node`。
13. repeat-3、repeat-10、held-out、成本、缓存和 trace 审查通过。
