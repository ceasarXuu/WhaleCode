# R7.1 持久化 Canonical Map Store 实施设计

> 状态：A0.1 合同冻结  
> 适用范围：R7.1-A0  
> 上游总账：`40-r7.1-milestone-baseline.md`  
> 根因记录：`coe/2026-07-24-21-21-r7-canonical-map-persistence-ownership.md`

## 1. 目标

R7.1-A0 把 TaskSpace Map 从 Session-local Runtime 和 rollout 恢复链路迁移到独立持久化
Map Store。迁移完成后：

- Map Store 是 Map、node、edge、lease、result、trace 和 revision 的唯一事实源；
- Runtime 只执行 Agent 请求的操作、硬规则校验和 projection 构造；
- Session 只持有 Map handle 和按 Store revision 校验的可丢弃 Runtime 缓存；
- rollout 只保存自然上下文、Tool 事实、审计事件和 Map revision 引用；
- resume、fork 和 child 通过线程绑定访问同一份 Map，不从 rollout 重建、复制或派生 Map；
- Store 不可用、revision 冲突或事务失败时返回事实错误，不静默回退到内存或 rollout。

本阶段不改变 Agent 的图设计语义、projection policy、普通 Tool 合同或非终态连续动作合同。

## 2. 所有权合同

### 2.1 唯一事实源

| 组件 | 持有内容 | 可以做 | 禁止做 |
|---|---|---|---|
| Map Store | 完整 `ActionMapSnapshot`、Store revision、绑定和提交幂等记录 | 原子创建、读取、绑定、CAS 提交 | 解释目标、自动推进节点、合并语义冲突 |
| Runtime | 当前 Store revision 对应的内存表示 | 执行 typed operation、校验硬规则、构造 snapshot/projection | 脱离 Store 成为事实源、自动重试语义操作 |
| Session | `map_id`、`store_revision`、Map principal、Runtime cache | 加载、提交、失效缓存、记录 actor | 通过 rollout 恢复 Map、维护第二份 authoritative Map |
| rollout | 对话、Tool 事实、审计事件、Map 引用 | 回放自然上下文和审计轨迹 | 携带可用于恢复 Map 的 snapshot/delta |
| Agent | Map/node/lease/graph revision 引用 | 决定图结构和状态变更 | 绕过 TaskSpace 硬规则 |

Runtime cache 的正确性条件是：

```text
cache.map_id == handle.map_id
and cache.store_revision == handle.store_revision
and cache.snapshot_sha256 == Store 当前记录
```

任一条件不成立时必须丢弃并从 Store 重新加载，不能局部修补缓存。

### 2.2 两类 revision

- `graph_revision`：Map 领域 revision，由 Agent 在图操作中显式携带，服务状态机硬规则。
- `store_revision`：持久化聚合体 revision，每次 Store 提交递增，服务并发和缓存一致性。

二者不得复用。Tool 结果、lease、trace 等不一定改变图，但仍会改变 canonical Map，因此会推进
`store_revision`。

### 2.3 Map 身份与线程绑定

- `map_id` 必须全局唯一，不再使用每个 Runtime 都会重复生成的 `map-1`。
- 首次进入 TaskSpace 时，Runtime 机械创建空 Map；`map_id` 由当前根线程身份生成，不包含语义。
- `owner_thread_id` 是不可变的来源信息，不是排他运行锁。
- `taskspace_map_bindings` 记录 owner、resume、fork、child 对同一 `map_id` 的访问关系。
- resume 使用原线程 binding；fork 使用来源线程 binding；child 使用
  `SessionSource::SubAgent::ThreadSpawn.parent_thread_id` 的 binding。
- fork 不复制 Map。多个绑定并发写同一 Map 时，Store CAS 只允许一个 expected revision 成功。
- CAS 冲突原样返回当前 revision，Agent 决定读取后如何继续；Runtime 不自动重放、合并或重试操作。

现有 Map 内部的 `owner_session_id` 和主 lease 身份在 A0 作为 Map principal 使用。fork session 通过
Store binding 获得 principal 权限，但结构化日志始终同时记录真实 actor thread，避免审计身份丢失。

## 3. 持久化模型

复用 `codex-state` 的 SQLx + SQLite WAL 数据库，新增迁移，不新建数据库或平行存储框架。

### 3.1 `taskspace_maps`

| 字段 | 约束 | 含义 |
|---|---|---|
| `map_id` | PRIMARY KEY | 全局 Map 身份 |
| `owner_thread_id` | NOT NULL | Map 来源线程 |
| `snapshot_json` | NOT NULL | 完整 canonical 聚合体 |
| `snapshot_sha256` | NOT NULL | 完整性和幂等校验 |
| `store_revision` | NOT NULL | Store CAS revision |
| `graph_revision` | NOT NULL | 当前领域 revision，空 Map 为 0 |
| `complete` | NOT NULL | 最终 Map 是否闭合 |
| `created_at_ms` / `updated_at_ms` | NOT NULL | 机械时间戳 |

使用单行 JSON 聚合体是刻意选择：A0 的首要目标是保证 Map 全部组成部分在同一事务边界提交，避免
node/edge/lease/result 分表后出现半状态。后续若需要查询投影，应从 canonical 行派生只读索引，不能反向成为
事实源。

### 3.2 `taskspace_map_bindings`

| 字段 | 约束 | 含义 |
|---|---|---|
| `thread_id` | PRIMARY KEY | 访问 Map 的线程 |
| `map_id` | FK | canonical Map |
| `relation` | CHECK | `owner`、`resume`、`fork`、`child` |
| `parent_thread_id` | NULLABLE | fork/child 来源 |
| `node_id` / `lease_id` | NULLABLE | child handoff 引用 |
| `created_at_ms` / `updated_at_ms` | NOT NULL | 机械时间戳 |

### 3.3 `taskspace_map_commits`

| 字段 | 约束 | 含义 |
|---|---|---|
| `commit_id` | PRIMARY KEY | 调用方生成的幂等键 |
| `map_id` | FK | 目标 Map |
| `expected_store_revision` | NOT NULL | 调用前 revision |
| `result_store_revision` | NOT NULL | 提交后 revision |
| `snapshot_sha256` | NOT NULL | 提交结果 |
| `operation` | NOT NULL | 机械操作名 |
| `actor_thread_id` | NOT NULL | 真实发起线程 |
| `created_at_ms` | NOT NULL | 时间戳 |

同一个 `commit_id` 再次提交相同结果返回 `IdempotentReplay`；键相同但内容不同属于合同错误。

## 4. Repository 合同

`codex-state::StateRuntime` 提供：

```rust
create_taskspace_map(...)
load_taskspace_map_for_thread(...)
bind_thread_to_taskspace_map(...)
compare_and_swap_taskspace_map(...)
```

事务规则：

1. 写事务使用 `BEGIN IMMEDIATE`；
2. 先检查 `commit_id`；
3. CAS 使用 `WHERE map_id = ? AND store_revision = ?`；
4. Map 行、binding 和 commit 行在同一事务中提交；
5. `rows_affected == 0` 返回 `Conflict` 和当前记录；
6. JSON 反序列化、hash 不一致或 revision 越界均返回错误，不能忽略；
7. State DB 缺失时 TaskSpace 激活失败，Standard 保持原行为。

SQLite 保证同一连接上的显式事务不会暴露半提交；SQLx `Transaction` 在未 commit 时 drop 会回滚。CAS
用于检测多个 Session cache 基于同一 revision 写入，而不是替代领域状态机。

## 5. 生产路径

### 5.1 新 TaskSpace

1. `SetMapRuntimeMode(Experiment)` 在候选 Runtime 中机械创建空 Map；
2. Store 原子创建 Map、owner binding 和首条 commit；
3. 成功后安装 Runtime cache 和 handle；
4. 失败则不切换 Session 内状态。

### 5.2 普通操作

1. 从 Session 复制与 handle revision 一致的 Runtime candidate；
2. Runtime 执行 Agent 指定操作和硬规则校验；
3. candidate snapshot 通过 Store CAS 提交；
4. Store 成功后才安装 candidate；
5. 最后发送领域事实事件和只含引用的 Store commit 事件。

### 5.3 resume、fork 和 child

1. Session 启动先根据当前线程或来源线程查 binding；
2. fork/child 在 Store 中新增指向同一 Map 的 binding；
3. 从 Store 加载当前 snapshot 并恢复 Runtime cache；
4. rollout reconstruction 只恢复自然上下文和非 canonical 审计事件；
5. 禁止调用 rollout snapshot/delta reducer 或以历史事件覆盖 Store。

### 5.4 terminal

`finish_map` 继续由 Agent 显式提交。Runtime 在 candidate 中验证 frontier，Store CAS 持久化完整终态后才安装
cache。rollout 中只记录 `GraphRevisionCommitted`、terminal trace 和 Map Store revision 引用，不再嵌入终态
snapshot。

## 6. 失败语义与日志

永久结构化事件：

- `taskspace.map_store_created`
- `taskspace.map_store_loaded`
- `taskspace.map_store_thread_bound`
- `taskspace.map_store_committed`
- `taskspace.map_store_conflict`
- `taskspace.map_store_integrity_failed`

公共字段：

```text
map_id, store_revision, graph_revision, actor_thread_id,
owner_thread_id, node_id, lease_id, operation, commit_id, reason_code
```

日志不记录 goal、summary、Tool 输出正文或 reasoning。Store 冲突返回事实：

```text
expected_store_revision, current_store_revision, map_id
```

不得把冲突改写为“Agent 应该做什么”，也不得自动重试原语义操作。

## 7. 删除清单

A0 不做兼容，因此必须删除：

- `taskspace_replay` 生产模块和 `debug taskspace-replay`；
- `SnapshotUpdated`、`SnapshotDelta` 的协议结构和 rollout 写入；
- terminal 事件中的 `snapshot` 与 `snapshot_sha256`；
- `SessionState::action_map_checkpoint`；
- rollout reconstruction 中的 snapshot restore、delta apply 和 fork rebind；
- 任何“Store 缺失时从 rollout 恢复”或“Store 写失败时只保留内存”的 fallback。

`ActionMapRuntimeState::snapshot/restore_snapshot` 作为 Store 编解码边界保留；它们不再是 rollout replay API。

## 8. 验收

### 8.1 Repository

- migration、create/load/bind；
- CAS 成功和 revision 冲突；
- commit 幂等重放和键冲突；
- snapshot hash/JSON 完整性失败；
- 两个并发 writer 只允许一个提交；
-事务失败后 Map、binding、commit 都不出现半状态。

### 8.2 生产路径

- 新 TaskSpace 创建持久化空 Map；
- 初始化、图变更、节点转换、lease、Tool 结果、finish 均推进 Store revision；
- 重启/resume 读取同一 map/revision；
- fork/child binding 指向同一 Map，不复制 snapshot；
- 截断 rollout 后 Map 仍可读取；
- 删除 Store 后 resume 明确失败，不从 rollout 重建；
- Standard 不创建 Map Store 数据，不改变 Tool schema。

### 8.3 残留扫描

以下生产引用必须为零：

```text
taskspace_replay
SnapshotUpdated
SnapshotDelta
action_map_checkpoint
build_snapshot_delta
apply_snapshot_delta
taskspace_snapshot_restore
```

历史设计、COE 和测试证据可以保留旧术语，但必须明确标记为历史，不得作为当前合同引用。
