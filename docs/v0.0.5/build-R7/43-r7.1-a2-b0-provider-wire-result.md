## 1. 验证目标

A2-B0 只验证真实 DeepSeek Chat wire 是否能够承载 A2 v3.0 的响应级动作归属合同：

1. 一个 `taskspace_control` 与多个原生 sibling function calls 能否出现在同一完整 response；
2. control 的 `actions[]` 能否按顺序、Tool 名称和 Agent 声明的 `node_id` 与 sibling calls 机械配对；
3. Function、Patch、MCP、ToolSearch 和客户端 WebSearch 是否保持各自原生参数形态；
4. provider 无法进入完整客户端 manifest 的能力是否能在执行前明确分类并失败闭合。

本阶段不执行返回的业务 Tool，不接入生产 Runtime，也不验证自然编码任务中的 Agent 遵循率。

所有正向 response 均以 `finish_reason=tool_calls` 完整返回；Tool 名称和顺序、`actions[]` 配对及
逐动作 `node_id` 全部一致。Patch 场景 3/3 保持原始 patch 文本逐字相等。两个负向场景均在 provider
生成和客户端执行前以 HTTP 400 稳定拒绝。

缓存数据只描述短小且并行发出的合成探针，不是 projection 策略成本结果，也不进入 R7 的商业成本晋升结论。

## 4. 探针自身暴露的问题

第一次运行中，`taskspace_control.parameters` 顶层只有 `anyOf`，缺少 DeepSeek 要求的显式
`type: object`，全部正向请求在生成前被拒绝。修复后增加了确定性合同测试，禁止再次退化。

第二次运行仍携带旧的 `tool_choice=required` 假设，与 thinking 模式和当前生产 `auto` 路径不一致。
修复后正向场景使用生产等价的 `auto`，并把 `thinking + required` 留作负向合同，避免旧强制切换机制回流。

分析器同时改为把 HTTP 级 provider 拒绝单独记为 `provider_request_rejected`，不再伪装成 Agent
动作顺序、manifest 或 patch 语义错误。

## 5. 阶段结论

A2-B0 验收通过，可以进入 A2-B1。成立的结论是 provider wire 和受引导的响应生成具备目标承载能力；
不成立的结论包括：

- B1-B4 的 Store、schema、preflight、dispatch、反馈和 subagent 生产迁移尚未实现；
- 尚未证明自然任务中的连续动作稳定性；
- 尚未关闭 R-10、R-19、R-24 或 R-25；
- 尚未改变 72.5% 的生产实现完成度。

后续 B1 必须继续保持 `tool_choice=auto`、普通 Tool 零侵入、Agent 逐动作声明 `node_id`、Runtime
不维护 current/next，以及无旧 wire 兼容路径。
