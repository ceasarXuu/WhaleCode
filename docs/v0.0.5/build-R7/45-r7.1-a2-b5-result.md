## 1. 阶段结论

A2-B5 的生产实现和本地工程门已完成。TaskSpace 现在只有一份由 Store 持久化的 canonical Map；Agent 通过
`taskspace_control` 声明图变更、动作归属和 Map 生命周期，Runtime 只执行机械解析、硬约束校验、原子提交、
原生 Tool dispatch 与事实记录。

当前顶层 action 固定为：

```text
initialize_and_execute
execute
reopen_map
read_map
read_output_ref
finish_map
```

`finish_map` 原子完成 Agent 声明的最终 Work 节点并写入显式 Finish；Root 和 Finish 的完成状态由事实派生。
用户反馈任务未完成时，`reopen_map` 将同一 Map 从 `closed` 恢复为 `active`，原 Finish 进入只读历史，新 Work、
edges、actions 和原生 sibling Tools 可以在同一 response 中继续推进。

本阶段只关闭工程实现门。R-10、R-19、R-22 仍需 A2-C 四臂真实模型 repeat-3 验证，不能由单元测试或静态合同
提前关闭，也不能据此宣称请求数、token、缓存、耗时或任务成功率收益。

## 2. 生产合同

| 领域 | 当前唯一合同 |
|---|---|
| Map 事实源 | `codex-state` Store 中的 canonical Map v2；restart/resume/fork/child 读取同一持久记录 |
| 图模型 | 唯一 Root、多个 Work、显式 Finish；每个非 Root 节点至少一条入边，允许多前置依赖 |
| 节点状态 | Waiting、Ready、InFlight、Blocked、Completed 从依赖、completion、block、reservation、result 派生 |
| Agent 权限 | Agent 声明 Work、edges、每个 action 的 `node_id + tool`、最终 Work IDs 和 reopen 后续动作 |
| Runtime 边界 | 只校验数量、名称、顺序、图事实、revision、reservation 和生命周期硬规则 |
| 普通 Tool | schema、参数、handler、权限、sandbox、结果语义保持原生，不感知 `node_id` |
| 响应顺序 | Runtime 在 response 外层校验 control manifest 与原生 sibling Tool calls 的数量和顺序 |
| Patch | 每个 response 最多一个 Patch；Patch 继续由原生 Tool 执行 |
| 结果反馈 | 原始成功或失败结果按 Agent 声明的 action 归属写入事实记录，不做语义重写 |
| Projection | 三种策略共用同一 Map、Tool、状态机和反馈路径；差异仅在 projection 进入 context 的方式 |

生产路径不再保留 `current/current_binding/current_node`、持久化 `Open`、singleton main lease、
`bind_node`、`complete_then_continue`、`rework_node`、普通 Tool decoration 或 rollout Map rebuild。

## 3. 生命周期

### 3.1 初始化与执行

`initialize_and_execute` 从 `absent` 创建 Root、Work 和 edges，同时必须声明至少一个 action，并在同一 response
携带等量的原生 sibling Tool calls。初始化不是一个可单独消耗 provider request 的记账动作。

### 3.2 活跃推进

`execute` 可以创建或更新多个 Work/edges，并为多个尚未闭合的节点声明 actions。系统不存在 `current node`；
Runtime 不替 Agent 选择默认节点，也不根据普通 Tool 参数推断动作意义。

### 3.3 关闭

`finish_map` 只允许 `active -> closed`。Agent 必须显式声明最终 Work IDs；Store 在同一 transaction 中记录这些
Work 的 completion 和当前 Finish。Root/Finish 完成是可重建的派生结果，不是第二份生命周期事实。

### 3.4 重新打开

`reopen_map` 只允许 `closed -> active`，其产品语义只是让 Agent 在用户反馈后继续同一个任务 Map。它不引入
“返工”分类，也不改写既有 Work 历史；旧 Finish 进入 terminal history，新的显式 Finish 仍只能由 Agent 最终
调用 `finish_map` 创建。

## 4. 清理与可观测性

## 6. 对抗性审查

首名不继承当前会话上下文的 fresh、只读 reviewer 检查 `cab37129c..302ea5db3` 后给出 2 个 blocking 和
4 个 non-blocking finding：

1. 接受：CLI、TUI、App Server 和 Core 的 reborn/restart 入口可将 canonical Map 写成 `null`；
2. 接受：空或重复 `call_id` 可越过 preflight，在 reservation commit 后失败；
3. 接受：projection 将 Root 错放入 `active_frontier`；
4. 接受：lifecycle oracle 对 InFlight final Work 的表述与实现冲突；
5. 接受：活跃 benchmark 仍按 R6 lease/blank-map marker 解释动作顺序；
6. 接受：缺少 invalid initialize/execute/reopen 的真实 StateDB 零提交覆盖。

`d87d1af35` 已逐项修复，并额外清理默认 harness 的旧 action/projection fixture、22 个永久禁用的旧
multi-agent binding/lease 测试，以及生产 manifest 未逐项验证 L5 hash 的门禁缺口。

第二名不继承当前会话上下文的 fresh、只读 reviewer 针对固定提交 `d87d1af35` 完成 closure review，
结果为 `0 blocking / 0 non-blocking`，并明确给出 closure PASS。它确认：

1. reborn/restart 已从 CLI、TUI、App Server、protocol 和 Core 生产路径删除；
2. response identity 在 Store mutation 前校验，runtime 防御层也不允许无效 identity 进入 transaction；
3. prepared calls 按 response index 配对，不再通过 `call_id` HashMap 折叠；
4. `active_frontier` 只包含 Work，Root 只保留为全局 Map 事实；
5. 当前 observer、fixture、StateDB 集成测试和 B5 残留门均使用同一现行合同；
6. 旧字符串仅存在于历史文档、明确 obsolete artifact 或负向拒绝测试，不是生产可达逻辑。

完整审查输入、launch/freshness 记录、逐项 disposition 和闭环证据见

## 7. 后续边界

A2-B5 通过对抗性验收后，下一阶段是 A2-C：

1. 使用同一 Docker image、model、binary、capability set；
2. 运行 Standard、map-always、map-append、map-request 四臂；
3. simple/complex 每臂 repeat 3；
4. 逐 trace 验证 R-10、R-19、R-22、Map 形状、动作归属、单 Patch 和反馈完整性；
5. 只有结构门全部通过后才进入 repeat-10 和 held-out。

本阶段不修改 acceptance baseline，不提前晋升任何 projection policy。
