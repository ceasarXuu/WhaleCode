## 6. 两个确定性根因

### 6.1 公开 Tool identity 被内部 dispatch identity 覆盖

provider 向 Agent 暴露 `exec_command`。Router 为复用 shell handler 将其归一化为 `shell_command`；sequence
preflight 随后直接比较 `actions[].tool` 与归一化后的名字。Agent 按公开合同填写正确名称，Runtime 却以内部实现
名拒绝。

正确边界：

- Agent manifest、preflight 和 Map reservation 使用 provider-visible Tool identity；
- Router/handler 使用 internal dispatch identity；
- ordinary Tool schema、参数和 handler 不增加 TaskSpace 字段。

### 6.2 response-final revision 反馈缺失

`TaskSpaceResponseCommitV1.revision_after` 只表示 mutations/reservations prepare 后的中间 revision。每个 sibling
ordinary result 释放 reservation 时继续提交 Map，但这些 revision 只存在 Store/日志，不进入 model-visible
feedback。Agent 下一请求使用最后被明确告知的 revision，随后被 stale reject。

这是反馈层语义缺失。修复不得改写普通 Tool 原生输出，也不得让 Runtime 代替 Agent 选择动作；应在完整 response
执行完成后提供机械的 final commit receipt。

## 8. Map 形状

- simple：9/9 均为 5 nodes / 4 edges，`Root -> explore -> fix -> verify -> Finish`；
- complex：3-6 nodes、2-5 edges，全部 rooted、无孤立节点、Root/Finish 唯一；
- complex Map 全部选择线性依赖链；多数节点目标与实际阶段一致；
- `map-request repeat 2` 退化为 `Root -> explore -> Finish`，所有修复和验证都归入 `explore`，属于 Map 质量弱化；
- 当前样本不足以评价多前置依赖或分支 DAG 质量，不据此新增 Runtime 约束。

R-24/R-25 未回归：没有 current node、singleton binding 或持久化 Open；所有动作归属来自 Agent manifest。

## 10. 阶段裁决

A2-C 的运行工作完成，但 acceptance 失败。后续顺序应为：

1. 单变量修复 provider-visible Tool identity；
2. 单变量修复 response-final revision 反馈；
3. 收敛 `mutations` 空数组、completed-node ownership 和单 Patch 的 L2/L4 合同；
4. 用同一两个样本重新执行四臂 repeat-3；
5. 只有首请求初始化、sequence/state failure 和 multi-Patch 均不再结构性复现，才进入 A2-D。

以上五项已在产品确认后完成工程修复，但本节保留 A2-C 原始裁决。当前仍不进入 A2-D，必须先用同一矩阵重跑
A2-C 验收。

## 11. A2-C 五项修复状态

2026-07-29 已完成以下修复：

1. `ToolCall` 同时保存 provider-visible identity 与 internal dispatch identity；manifest、preflight、reservation、
   sequence hash 和 Agent 可见日志只使用前者，handler dispatch 只使用后者。
2. 在普通 sibling Tool 输出和 result attribution 全部结束后，从独立 Map Store 读取 canonical Map，并追加独立
   `TaskSpaceResponseFinalReceiptV1` 事实回执。prepare revision、普通 Tool 原生结果和 response-final revision 不再
   相互覆盖。
3. `execute.mutations` 从必填字段改为可省略，wire 省略时解析为空列表。
4. L2/L4 同时公开“本 transaction 完成或阻塞的节点不能拥有 sibling action”。
5. L2/L4 同时公开“每个 response 最多一个 `apply_patch`”；Runtime 继续只做原有 response-wide 原子硬门。

新增结构化日志 `taskspace_response_final_receipt_emitted`，benchmark observer 同步记录 final receipt 总数、完整/
不完整数和最新 canonical revision。聚焦 Rust 与 observer 回归已经通过；四臂 repeat-3 live rerun 尚未执行，因此
R-10/R-22 仍保持 open，修复不能仅凭单元测试宣告产品验收。
