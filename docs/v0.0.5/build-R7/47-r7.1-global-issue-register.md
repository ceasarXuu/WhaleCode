## 1. 唯一性声明

本文件是 R7.1 当前已知问题、优先级、状态和关闭标准的唯一权威清单。

其他文档的职责严格限定为：

- `38-r7-five-layer-integrated-change-constraints.md`：维护不可回退的架构约束和准入门；
- `40-r7.1-milestone-baseline.md`：维护里程碑入口、已完成能力和推进边界；
- 阶段结果文档：记录某一次运行或实现的历史证据；
- `/coe`：记录问题假设、诊断过程和证据链；
- benchmark artifact：保存可重算的原始运行事实。

其他文档可以引用本清单中的问题 ID，但不得独立新增当前问题、修改问题状态、重新统计开放问题数量，或建立平行
“遗留问题清单”。发生冲突时，以本文件为准。

## 2. 维护规则

1. 每个问题使用稳定 ID `R71-GI-xxx`，不得复用或重编号；
2. 新发现的问题必须先与现有条目去重，再决定新增、补充证据或拆分；
3. 同一问题的不同表现写入同一条目的 Symptoms，不重复建账；
4. 同一实现造成两个独立验收失败时可以拆分，例如 revision 语义正确性与 Provider 缓存正确性；
5. 状态只允许：
   - `open-confirmed`：问题和主要因果已由证据确认；
   - `open-investigating`：问题确认，但根因尚未收敛；
   - `implementing`：修复方案已批准并正在实施；
   - `validating`：实现完成，等待真实样本验收；
   - `closed`：关闭标准全部满足；
6. 单元测试只能证明工程接线，不能单独关闭真实模型行为或成本问题；
7. 问题关闭后保留原 ID，移入本文件的关闭记录，不删除历史；
8. 修改问题数量、优先级、状态、根因或关闭标准时，必须同步更新 `Updated` 和变更记录。

## 4. 问题详情

### R71-GI-001：response-final revision 存在双重权威

- Priority: P0
- Status: open-confirmed
- Symptoms:
  - control prepare 返回 `revision_after=N`；
  - sibling result attribution 后 canonical Map 已推进到 `N+K`；
  - 独立 receipt/projection 返回最终 revision，但 Agent 仍使用 prepare revision；
  - rerun 中 14 个 response stale 和 3 个 `finish_map` stale 全部符合该路径。
- Root cause:
  - 中间 revision 与最终 revision 同时作为成功事实进入上下文；
  - 最终值没有收敛为同一个 `taskspace_control` Tool result 中唯一可用于下一次提交的 revision。
- Boundary:
  - Runtime 只反馈机械 revision 事实；
  - Runtime 不替 Agent 选择动作或自动修复提交。
- Close criteria:
  - sibling attribution 完成后，同一 control Tool result 返回唯一权威 `canonical_revision`；
  - 中间值如需保留，只能使用明确的诊断名称，不能与下一提交 revision 竞争；
  - 三种 projection policy 的同口径 repeat-3 中，隐藏 result attribution 导致的 stale 为 0；
  - 普通 Tool 原生输出保持不变。
- Evidence:
  - [`46-r7.1-a2-c-repeat3-result.md`](46-r7.1-a2-c-repeat3-result.md)
  - [`../../../coe/2026-07-29-04-11-r7-a2-c-revision-feedback-gap.md`](../../../coe/2026-07-29-04-11-r7-a2-c-revision-feedback-gap.md)

### R71-GI-002：Final Receipt carrier 确定性破坏 Provider 缓存

- Priority: P0
- Status: open-confirmed
- Symptoms:
  - 独立 receipt 以 developer history 进入 Session；
  - DeepSeek ChatCompletions wire 将其表示为中途 system message；
  - `map-append` 紧跟 receipt 的请求 35/35 缓存退回基础前缀；
  - `map-append` request-2+ cache 从 95.11% 降到 57.04%。
- Root cause:
  - 最终状态事实使用了会改变消息角色与缓存分段的错误 carrier。
- Boundary:
  - 不得删除最终 revision 事实来换取缓存；
  - 不得改写普通 Tool 原生结果；
  - 三种 projection policy 共用同一 control feedback 实现。
- Close criteria:
  - 删除独立 developer/system receipt；
  - final revision 通过同一 control Tool result 返回；
  - provider wire 不新增 receipt system message；
  - 同环境 `map-append` request-2+ cache 恢复到不低于 90%，且不存在 receipt 相关系统性低点；
  - Observer 自动输出 carrier role 和 cache 对齐结果。
- Evidence:
  - [`46-r7.1-a2-c-repeat3-result.md`](46-r7.1-a2-c-repeat3-result.md)
  - [`../../../coe/2026-07-29-04-11-r7-a2-c-revision-feedback-gap.md`](../../../coe/2026-07-29-04-11-r7-a2-c-revision-feedback-gap.md)

### R71-GI-003：TaskSpace response 动作框架持续遵循不稳定

- Priority: P0
- Status: open-confirmed
- Symptoms:
  - 18 个首请求中，14 个直接调用 ordinary Tool，3 个 solo init mismatch，只有 1 个提交 `init + actions`；
  - 63 个 `taskspace_control_required` 中，41 个发生在 Map 已初始化后；
  - 另有 16 个 action count mismatch 和 2 个 control order failure；
  - 59/63 的下一 response 会携带 control，但后续又重新遗漏。
- Root cause:
  - 当前合同要求一次 provider response 同时满足多个 sibling Tool call 的类型、顺序和数量；
  - 单个 Tool JSON schema 无法完整表达跨 Tool-call 序列，L1/L2 文本也没有稳定形成默认动作框架。
- Boundary:
  - ordinary Tool schema 保持原生；
  - node 归属由 Agent 声明；
  - Runtime 只做 response grammar 硬校验，不代替 Agent 生成或补全动作。
- Close criteria:
  - 首请求 `initialize_and_execute + matching ordinary actions` 提交率达到 18/18；
  - Map 初始化后 ordinary-only response 为 0；
  - action count mismatch 和 control order failure 均为 0；
  - 不通过侵入普通 Tool schema、动态 capability 切换或 Runtime 自动补 control 实现。
- Evidence:
  - [`46-r7.1-a2-c-repeat3-result.md`](46-r7.1-a2-c-repeat3-result.md)
  - [`../../../coe/2026-07-29-19-18-r7-a2-c-rejection-taxonomy.md`](../../../coe/2026-07-29-19-18-r7-a2-c-rejection-taxonomy.md)

  - `complete_node + successor actions` 的合法连续动作路径稳定执行；
  - 多活跃节点仍由 Agent 逐 action 声明 `node_id`，不引入 current node。

### R71-GI-007：Observer 失败分类与缓存归因口径不完整

- Priority: P1
- Status: open-confirmed
- Symptoms:
  - 同一矩阵同时输出 82 个 `tool_sequence_protocol_failure_requests`、0 个
    `taskspace_protocol_failure_requests` 和 53 个 `control_failures`；
  - sibling 复制反馈容易被误算成多个独立 violation；
  - 矩阵报告没有自动输出 receipt-before cache 分组；
  - 早期分析曾把全部 reservation failure 错误归因到 ownership。
- Root cause:
  - sequence、control-call、state、ordinary failure 的统计集合有重叠或隐含边界；
  - request-level 根因和 provider carrier/cache 没有成为一等字段。
- Close criteria:
  - 每个 request 进入唯一一级 failure class，并允许附加非互斥 secondary tags；
  - 一级分类总和能够与 provider request 总数对账；
  - state failure 直接汇总底层 violation，不重复 sibling copies；
  - 自动输出 receipt message role、receipt delta 和下一请求 cache；
  - 报告中明确区分业务成功、Tool 成功、协议成功和 Map terminal。

### R71-GI-008：TaskSpace 固定上下文成本尚未完成准入

- Priority: P1
- Status: open-confirmed
- Symptoms:
  - Standard Tool section 平均 5,299 token/request；
  - TaskSpace Tool section 平均 6,792 token/request，固定增加约 1,493；
  - 当前候选虽从历史 46,926 bytes/request 降到 26,822 bytes/request，但 held-out 尚未完成；
  - 动态拒绝和 receipt 回归尚未消除，当前总成本不能代表稳态成本。
- Root cause:
  - 唯一 control Tool 有必要固定成本；
  - 当前无法在协议拒绝和缓存回归未解决时判断其中多少是不可约成本、多少仍是重复合同。
- Boundary:
  - shared ordinary Tool 相对 Standard 的 schema 增量必须为 0；
  - 不通过删除必要硬合同、压缩语义或动态切换 Tool schema 降成本。
- Close criteria:
  - 完成唯一 control schema 字段级成本审计，删除重复但保留完整机械合同；
  - 同 capability set 下 shared ordinary Tool bytes 与 Standard 完全相同；
  - TaskSpace Tool section 保持低于 46,926 bytes/request；
  - R71-GI-001、002、003 修复后重跑 repeat-3 和 held-out，报告稳定 request、input、cache 和 wall time；
  - R-19 所有验收条件通过。
