## 1. 唯一编号规则

R7.1 从本文件起只使用一组当前执行编号：

```text
R71-<阶段>.<任务>
```

- `R71-01` 至 `R71-07` 表示严格有序的当前阶段；
- `.1`、`.2`、`.3` 表示阶段内部可以独立实现和验收的任务；
- 阶段编号同时表达主执行顺序，不再额外建立 `W0/W0B/W1` 或新的 Phase 别名；
- 严重度只使用“阻断级”“高”，不再使用容易与阶段混淆的 `P0/P1`；
- `FLA-*`、`A2-*`、`W*`、`R71-GI-*` 只允许出现在历史证据和第 8 节迁移表中；
- 新问题先与现有任务去重；只有独立根因、独立修复和独立关闭标准同时成立时才新增任务；
- 当前状态、依赖、关闭和问题数量只能在本文件更新。

状态只允许：

- `待实施`：问题和根因已确认，尚未开始实现；
- `返修`：已有实现被复审证伪，需要修复；
- `实施中`：方案已批准并正在实现；
- `待复验`：实现和聚焦测试完成，等待真实样本或独立审查；
- `已关闭`：全部关闭标准成立；
- `待准入`：非缺陷任务，等待所有前置门通过。

## 4. 任务定义与关闭标准

### R71-01.1：测量事实链

目标：让每个 provider request、Tool 结果、状态拒绝、token、cache 和 artifact provenance 都能由原始证据
唯一重算；测量失败只能降低证据资格，不能改变被测系统。

当前阻断：

- lifecycle normalizer 重复包装同一 violation；
- direct failure parser 接受重复属性、不一致 envelope 和 outer-success/inner-failure；
- provenance bytes 接受 string、fraction 或 missing；
- 合法 L5 carrier 被误计入静态 system 数，freshness finding 未进入 comparison eligibility。

关闭标准：

- 所有生产执行型 call/output 进入唯一一级分类，secondary tag 不重复制造根因；
- JSON、Int64、bytes、hash、carrier、request identity 和 provenance 任一不合法都 fail-closed；
- 静态 L1/L2 与动态 L5 分开计数，合法 L5 不破坏 fixed-contract identity；
- 新 sealed matrix 可由独立 reviewer 从 raw artifacts 重算；
- 本任务不得修改 model-visible Tool output、Tool schema、Map 状态或 dispatch 决策。

### R71-01.2：capability epoch

目标：用真正的 Tool capability 身份划分观测 epoch，而不是复用 conversation context window。

关闭标准：

- epoch 由稳定的 profile、provider capability 和 visible Tool set identity 决定；
- MCP inventory、connector selection 或 discovery 改变时，下一 provider request 显式进入新 epoch；
- Map revision、lifecycle 和 projection policy 不改变 capability epoch；
- provider wire、cache、benchmark 和 provenance 使用同一 epoch identity；
- 该身份只服务观测和归因，不反向修改 Agent 可见 capability。

### R71-02.1：Store hydrate 完整性

目标：持久化 Map 在进入 Runtime cache 前执行与初始化/写入侧相同的机械完整性校验。

关闭标准：

- hydrate 验证唯一 schema version、map_id 和全部 rooted-DAG 不变量；
- 旧 schema、孤立 Work、Root/Finish 不可达、多终点和错误 role fixture 确定性失败；
- 合法多父 DAG、非零 revision 的 resume/fork/child 读取同一 Map 成功；
- 失败不修改 active Map、cache 或 Store handle；
- Runtime 不修复、补边或从 rollout 重建非法 Map。

### R71-02.2：nested dispatcher 与单 Patch 边界

目标：所有 TaskSpace control/Patch 动作无论从顶层还是 nested 入口发起，都不能绕过同一个 response 级硬门。

关闭标准：

- CodeMode nested definitions 不暴露 `taskspace_control/apply_patch`，或者内部调用在执行前进入同一 preflight；
- 不建立第二套编排器，不修改普通 Tool 原生参数；
- preflight 逐项覆盖 node ownership、顺序、reservation、单 Patch 和零执行；
- Standard 不通过 nested `exec` 暴露 TaskSpace control；
- simple、complex 和 held-out 中 TaskSpace multi-Patch attempt 为 0。

本任务的硬边界实现属于阶段 02；真实模型 multi-Patch 行为必须在阶段 05 再复验，但不另建问题编号。

### R71-03.1：状态拒绝反馈

目标：Agent 直接看到 Runtime 已知的完整机械事实，且每个事实只出现一次。

关闭标准：

- failure 明确区分 canonical state 与 rejected candidate evaluated state；
- 节点、allowed states、canonical/evaluated predecessors、subjects 和 violation ordinal 完整保留；
- Function、Custom、ToolSearch 和直接 lifecycle carrier 语义一致；
- 同一 violation 不同时出现在 `actual.violations` 和嵌套 condition 中；
- 不注入建议、不自动改绑、不替 Agent 选择恢复动作；
- fresh live trace 中不再因 carrier 歧义发生同形重试。

### R71-03.2：唯一 final revision

目标：同一个 control Tool result 返回 sibling attribution 后唯一可用于下一提交的 canonical revision。

关闭标准：

- ordinary Tool attribution 完成后，control result 返回唯一 `canonical_revision`；
- prepare/intermediate revision 只能作为明确命名的诊断事实，不能与最终权威竞争；
- 三种 projection 的 repeat-3 中，隐藏 attribution 导致的 stale 为 0；
- 普通 Tool 原生输出保持不变。

### R71-03.3：Final Receipt carrier

目标：删除独立 developer/system receipt，同时不丢失最终 revision 和状态事实。

关闭标准：

- final revision 通过同一 control Tool result 返回；
- provider wire 不新增 receipt system message；
- `map-append` request-2+ cache 在同环境恢复到不低于 90%；
- Observer 自动报告 carrier role、cache delta 和 revision identity；
- 不通过删除事实或改变 projection 策略换取缓存。

### R71-04.1：响应动作合同

目标：让 Agent 稳定以 `control + actions` 推进 Map，同时保持普通 Tool schema、handler 和结果原生。

关闭标准：

- 首请求 `initialize_and_execute + matching ordinary actions` 达到验收样本全通过；
- Map 初始化后 ordinary-only response 为 0；
- action count、名称、顺序和 control-first mismatch 为 0；
- 非终态 lifecycle boundary 与后继真实动作位于同一 response；
- Runtime 只验证 Agent 声明，不补 control、不选节点、不推断归属；
- 不使用普通 Tool schema 装饰、动态 capability 切换或后置惩罚实现。

### R71-05.1：残余 lifecycle 行为

目标：在反馈和通用动作框架稳定后，重新判断 Waiting/Completed/Blocked reservation 是否仍结构性出现。

关闭标准：

- repeat-3 中 Waiting、Completed、Blocked 节点 reservation attempt 均为 0；
- `complete_node + successor actions` 合法连续执行；
- 多个 Ready/InFlight 节点继续由 Agent 逐 action 声明，不引入 current node；
- 同轮复验 `R71-02.2` 的 multi-Patch 行为门；
- 若旧现象不再出现，直接关闭，不按旧根因增加专用 Runtime 约束。

### R71-06.1：成本验收

目标：区分唯一 control Tool 的不可约固定成本与协议拒绝、缓存破坏、重复请求造成的可消除成本。

关闭标准：

- shared ordinary Tool 在 Standard/TaskSpace 的 schema bytes 完全相同；
- 唯一 control schema 完成字段级成本审计，机械合同无重复；
- simple、complex、held-out 的 repeat-3 全部报告正确率、request、input/output、cache 和 wall time；
- 所有成本差异都有 request-path 归因，不使用无效 observation 或重建值晋升；
- 所有前置问题关闭后，用户确认是否进入 `R71-07.1`。

### R71-07.1：repeat-10 与产品晋升

本项不是缺陷，只是最终准入门。

进入条件：

- `R71-01.1` 至 `R71-06.1` 全部关闭；
- 机器合同、candidate commit、binary、Docker image、model、skills、samples 和 capability set 冻结；
- repeat-3 与 held-out 没有未解释回归。

退出条件：

- Standard、`map-always`、`map-append`、`map-request` 的 simple/complex 每臂 repeat 10；
- 额外 held-out 对抗样本通过；
- 正确率、request、token、cache、wall time、Tool schema 和 Map 形状全部可复算；
- 用户明确批准更新 R7.1 acceptance baseline。

### 5.2 实施顺序

| 执行批次 | 工作 | 并行关系 | 停止条件 |
|---:|---|---|---|
| 1 | 01.1、01.2 | 两者可并行；01.2 验收等待 01.1 | 测量代码影响 Agent 可见语义时立即停止 |
| 2 | 02.1、02.2 | 彼此独立，也可与批次 1 的修复并行 | 需要新增语义决策或第二套编排器时立即停止 |
| 3 | 03.1、03.2 | 两者可并行 | 反馈开始建议下一步或改写普通 Tool 时立即停止 |
| 4 | 03.3 | 必须等待 03.2 | final revision 尚无合法 carrier 时不得删除 receipt |
| 5 | 04.1 | 等待 03 全部关闭 | 先重跑旧失败，再决定是否仍需实现 |
| 6 | 05.1 + 02.2 行为复验 | 同一矩阵并行观察 | 不为偶发模型错误增加专用 Runtime 语义 |
| 7 | 06.1 | 等待 01～05 全部关闭 | observation 不完整或 provenance 不可信即阻断 |
| 8 | 07.1 | 最后执行 | 未获用户批准不得晋升 |

优先级原则：

1. “阻断级”表示可破坏状态完整性、原子执行、唯一事实或核心动作协议；
2. “高”表示会使证据、反馈或成本结论不可信；
3. 执行顺序由依赖决定，不能用严重度跳过前置；
4. 可并行任务必须修改不同所有权模块，并分别提交、测试和记录证据。

## 6. 阶段验收纪律

1. 每个任务必须有根因假设、生产实现、正反测试、结构化日志和独立关闭记录；
2. 测量阶段不得修改被测语义，反馈阶段不得替 Agent 决策，硬边界阶段不得解释 Tool 业务内容；
3. 上游关闭后，下游先重跑旧失败样本；现象消失则关闭，不机械执行旧修复方案；
4. 单元测试只能关闭工程子门，真实模型遵循、成本和缓存必须使用同口径 Docker sample；
5. 每次只改变一个可归因策略；不同任务并行时分别构建候选和证据，不混合收益；
6. fresh adversarial review 只复审发生变更的独立 shard，避免再次建立无边界全量审查；
7. 任一任务失败不得恢复旧 wire、双 parser、rollout fallback、current node 或普通 Tool decoration。
