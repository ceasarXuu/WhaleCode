## 1. 唯一编号与原子边界

R7.1 从本文件起只使用一组当前执行编号：

```text
R71-<两位顺序号>
```

- `R71-01` 至 `R71-21` 各自就是一个可独立关闭的 Phase，不再设置阶段内子任务；
- 一个 Phase 只能有一个根因域、一个主要生产改动域和一套不依赖未来 Phase 的关闭证据；
- 路线决策、生产实现、行为复验、成本验收和产品晋升必须分开编号；
- 执行批次只表达并行调度，不形成新的阶段、状态或关闭口径；
- 严重度只使用“阻断级”“高”，不再使用容易与阶段混淆的 `P0/P1`；
- `FLA-*`、`A2-*`、`W*`、`R71-GI-*` 和上一版小数编号只允许出现在历史证据和第 6 节迁移表中；
- 新问题先与现有 Phase 去重；只有独立根因、独立改动域和独立关闭标准同时成立时才新增编号；
- 当前状态、依赖、关闭结论和数量只能在本文件更新。

状态只允许：

- `待实施`：根因和路线已确认，尚未开始生产实现；
- `返修`：已有实现被证伪，需要在原改动域修复；
- `待决策`：存在重大技术路线或产品取舍，必须形成证据并由用户确认；
- `待复验`：不预设仍需代码，先用可信证据重跑旧现象；
- `待判定`：是否触发取决于前一因果复验；
- `待准入`：非缺陷修复，等待全部前置门通过；
- `实施中`：当前唯一正在修改的 Phase；
- `已关闭`：本 Phase 的独立关闭标准全部成立。

## 3. 原子 Phase 定义

### R71-01：direct failure carrier 证据合同

- 类型：测量返修。
- 入口：保留 raw call/output 和 Round 13 Shard B 反例。
- 唯一改动域：direct failure evidence adapter 的 JSON 解析、envelope 校验和一级分类。
- 不包含：lifecycle 反馈文本、Tool schema、Map 状态和 Runtime dispatch。
- 产物：一个 fail-closed 的 direct failure record。
- 预期收益：外层成功、内层失败、重复属性或跨字段矛盾不再被误算为有效证据。
- 独立验收：重复属性、非法 schema/action、outer/inner 冲突、action/expected 冲突全部拒绝；ordinary Tool 不被误分为 TaskSpace failure；fresh Shard B 关闭。
- 退出：原始证据可以唯一重算 carrier、request、call 和失败原因。
- 回退：整单元提交回退；不得恢复宽松 parser 或第二套兼容解析。

### R71-02：artifact 数值与文件 provenance

- 类型：测量返修。
- 入口：Round 13 Shard C 的 string、fraction、missing bytes 反例。
- 唯一改动域：artifact provenance 的 exact Int64、文件长度、hash 和 final-status 来源。
- 不包含：failure taxonomy、合同层分类和 comparison eligibility。
- 产物：严格的 artifact provenance record。
- 预期收益：token、bytes 和文件事实不再被浮点转换、字符串转换或重建值污染。
- 独立验收：整数边界、fraction/string/missing、文件变更和 hash mismatch 正反 fixture 全通过；fresh Shard C 关闭。
- 退出：任一 artifact 的 bytes/hash/status 都能从文件事实独立重算。
- 回退：回退本单元；不得用默认值、近似值或 report-stage 重建补洞。

### R71-03：L1/L2/L5 合同层身份分类

- 类型：测量返修。
- 入口：合法 L5 carrier 被计入静态 system contract 的现有反例。
- 唯一改动域：Observer 的 contract layer classifier。
- 不包含：freshness、eligibility、projection 内容和 provider context 构造。
- 产物：静态 L1/L2 与动态 L5 的互斥身份记录。
- 预期收益：合法动态 carrier 不再破坏 fixed-contract identity 或夸大固定成本。
- 独立验收：L1、L2、L5-result、L5-projection、L5-lifecycle 正反 fixture 全部唯一分类。
- 退出：每个 provider-visible contract fragment 只有一个 primary layer identity。
- 回退：回退 classifier 提交；不得通过改动被测 wire 迎合分类器。

### R71-04：freshness 到 comparison eligibility 传播

- 类型：测量返修。
- 入口：freshness finding 已产生但 comparison 仍被标记 eligible 的反例。
- 唯一改动域：observation finding 到 comparison eligibility 的状态传播。
- 不包含：freshness 检测规则本身、样本运行和产品结论。
- 产物：带明确 reason code 的 eligible/ineligible 裁决。
- 预期收益：陈旧证据不能进入横向收益、成本或晋升结论。
- 独立验收：同一 fixture 只改变 freshness 时，eligibility 必须确定性翻转；理由可从 artifact 重算。
- 退出：不存在 `freshness=failed` 且 `comparison_eligible=true` 的产物。
- 回退：回退传播提交；不得静默忽略 finding。

### R71-05：Tool capability epoch 身份

- 类型：测量实现。
- 入口：当前把 conversation context window 误作 capability epoch 的实现。
- 唯一改动域：capability epoch identity 的生产者及 wire/cache/benchmark/provenance 消费接口。
- 不包含：Map revision、lifecycle、projection policy 和 Agent 可见 capability。
- 产物：由 profile、provider capability 和 visible Tool set 决定的统一 epoch。
- 预期收益：Tool inventory 变化可归因，Map 状态变化不再制造虚假 epoch。
- 独立验收：MCP inventory、connector/discovery 改变会切换 epoch；Map revision 和 projection 改变不会；所有消费者读取同一 identity。
- 退出：同一 provider request 在 wire、cache、benchmark 和 provenance 中只有一个 epoch。
- 回退：回退统一 identity 提交；不得保留新旧 epoch 双写。

### R71-06：Store hydrate 完整性

- 类型：Runtime 实现。
- 入口：Store hydrate 绕过 canonical schema 与 rooted-DAG 校验的生产路径。
- 唯一改动域：持久化 Map 进入 Runtime cache 前的 hydrate validator。
- 不包含：Map 修复、补边、rollout replay、Agent 恢复策略和 projection。
- 产物：与初始化/写入侧共用的 canonical hydrate validation。
- 预期收益：非法持久化 Map 无法污染 active Map 或后续 Agent 上下文。
- 独立验收：旧 schema、孤立 Work、不可达 Root/Finish、多终点、错误 role 确定性失败；合法多父 DAG、非零 revision 的 resume/fork/child 成功；失败保持 cache/handle 原子不变。
- 退出：Store 读侧与写侧共享同一组结构不变量。
- 回退：回退 hydrate 接入提交；不得恢复 rollout fallback 或自动修复。

### R71-07：nested capability 路线决策

- 类型：重大技术路线决策。
- 入口：nested definitions 可暴露 control/Patch，但顶层 response preflight 无法天然覆盖 nested 调用。
- 唯一改动域：决策文档；比较“nested 不暴露 control/Patch”与“nested 调用进入同一 preflight”。
- 不包含：生产代码、临时 fallback、双路径兼容和行为收益声明。
- 产物：外部资料、现有调用链证据、代价收益和用户批准的单一路线记录。
- 预期收益：先固定唯一责任边界，避免 R71-08 同时实现两个互斥架构。
- 独立验收：两条路线的 capability、原子性、普通 Tool 侵入、维护成本和回退方式均有证据；用户明确选择。
- 退出：R71-08 只有一个获批实现目标。
- 回退：本 Phase 不改生产行为；决策未获批准即保持阻断。

### R71-08：nested dispatcher 硬边界实现

- 类型：Runtime 实现。
- 入口：R71-07 的已批准路线。
- 唯一改动域：选定 nested capability inventory 或统一 preflight 接入点。
- 不包含：第二套编排器、普通 Tool 参数修改、Agent 节点选择和 multi-Patch 行为结论。
- 产物：顶层与 nested 入口共享且不可绕过的机械执行边界。
- 预期收益：control/Patch 不再因入口不同绕过 node ownership、顺序、reservation、单 Patch 或零执行门。
- 独立验收：top-level/nested 正反 fixture、Standard 隔离、零执行原子性和 capability inventory 测试通过。
- 退出：所有获准入口在执行前命中同一硬约束事实。
- 回退：整单元回退；不得保留未选路线或 nested 专用语义分支。

### R71-09：state rejection feedback 去重

- 类型：反馈返修。
- 入口：同一 lifecycle violation 同时出现在 `actual.violations` 与嵌套 condition。
- 唯一改动域：canonical lifecycle failure 到 Agent-visible Tool result 的映射。
- 不包含：Observer 分类、动作建议、自动改绑和 Runtime 状态决策。
- 产物：完整且每个事实只出现一次的 rejection carrier。
- 预期收益：Agent 能看到 canonical/evaluated state 的真实差异，不再被重复或歧义反馈诱发同形重试。
- 独立验收：节点、allowed states、predecessors、subjects、ordinal 完整；Function、Custom、ToolSearch 语义一致；fresh trace 无同形 carrier 重复。
- 退出：一个 violation 只有一个 canonical 表达位置。
- 回退：回退映射提交；不得把去重变成裁剪事实。

### R71-10：唯一 canonical final revision

- 类型：反馈实现。
- 入口：ordinary Tool attribution 后的最终 revision 未进入 control result。
- 唯一改动域：同一 response 内 control result 的 revision finalize 与回填。
- 不包含：Final Receipt 删除、projection 策略和普通 Tool 原生输出。
- 产物：唯一 `canonical_revision`；prepare/intermediate 只能作为非权威诊断字段。
- 预期收益：Agent 下一次提交只依赖一个最终 revision，不再猜测或使用 stale revision。
- 独立验收：sibling attribution、跳过动作、失败动作和多节点动作的 revision integration test；三种 projection 无隐藏 attribution stale。
- 退出：同一 response 不存在两个可竞争的权威 revision。
- 回退：回退 finalize 提交；不得恢复独立第二权威 carrier。

### R71-11：Final Receipt carrier 迁移

- 类型：上下文实现。
- 入口：R71-10 已提供合法 final revision carrier。
- 唯一改动域：删除独立 developer/system receipt，并把最终机械事实保留在同一 control Tool result。
- 不包含：删除状态事实、改变 projection policy 或压缩自然历史。
- 产物：无额外 system receipt 的 provider wire。
- 预期收益：消除错误 system history 与确定性缓存前缀破坏。
- 独立验收：wire role snapshot、revision identity、三种 projection repeat-3；同环境 `map-append` request-2+ cache 不低于 90%。
- 退出：Observer 能报告 carrier role、cache delta 和 revision identity，且 provider wire 无 receipt system message。
- 回退：回退 carrier 迁移提交；不得恢复双 carrier。

### R71-12：response action 异常因果复验

- 类型：诊断复验。
- 入口：R71-01～05、R71-09～11 全部关闭。
- 唯一改动域：旧失败 sample 的 sealed rerun、request trace 分类和因果报告。
- 不包含：Tool schema 修改、Runtime 惩罚、提示词加码和修复代码。
- 产物：初始化、ordinary-only、control-first、finish+next 的逐 request 因果报告。
- 预期收益：先判断旧异常是否由证据/反馈/carrier 修复自然消失，避免执行过期方案。
- 独立验收：同候选、同镜像、同模型、同 skills 的 repeat-3；每个失败都有原始 request/call/result 引用。
- 退出：明确裁决“问题消失”或“仍为结构性缺陷并给出唯一根因”。
- 回退：不改生产行为；无效 run 作废并保留无效原因。

### R71-13：response action 修复路线决策

- 预期收益：防止“修初始化又破坏连续动作”或反向回归。
- 独立验收：方案逐条对照五层架构、连续动作、普通 Tool 原生、Agent 声明 ownership 和 Runtime 硬边界；用户批准。

- 不包含：模型运行波动、request 次数、动态 projection 和产品晋升。
- 产物：Standard/TaskSpace 固定组件逐项成本表。
- 预期收益：识别不可约 control 成本与重复暴露、普通 Tool 侵入等可消除成本。
- 独立验收：shared ordinary Tool schema bytes 完全相同；每个 TaskSpace 独有字段只有一个责任层；账本可由 wire snapshot 重算。
- 退出：所有固定 input 差异都有唯一组件归属和保留理由。
- 回退：不改生产行为；若审计发现缺陷，新增独立原子 Phase，禁止在成本 Phase 顺手改代码。

### R71-18：动态执行成本验收

- 类型：成本验收。
- 入口：R71-01～17 全部关闭。
- 唯一改动域：simple、complex、held-out 的 repeat-3 执行与 request-path 成本归因。
- 不包含：新策略开发、repeat-10 和晋升决策。
- 产物：正确率、request、input/output、cache、wall time 和 Map 形状的 sealed report。
- 预期收益：把协议拒绝、缓存破坏、重复请求与三种 projection 固有成本分开。
- 独立验收：四臂同镜像、同模型、同 skills、同样本；总和、均值、中位数和逐 request trace 齐全；无无效 observation。
- 退出：所有成本差异可解释，held-out 无未归因回归。
- 回退：不改生产行为；环境或 provenance 不可信则整轮作废。

### R71-19：候选与评测环境冻结

- 类型：发布准备。
- 入口：R71-18 已关闭。
- 唯一改动域：candidate commit、binary、Docker image、model、skills、samples、capability set 和合同 hash 的冻结清单。
- 不包含：生产行为修改、样本迎合和评测执行。
- 产物：机器可校验的 candidate/environment manifest。
- 预期收益：repeat-10 期间不存在候选漂移或环境漂移。
- 独立验收：所有路径、digest、hash 和 capability identity 可解析且与实际运行入口一致。
- 退出：冻结后任一变化都会确定性阻断 R71-20。
- 回退：废弃冻结清单并重新进入本 Phase；不得覆盖旧 manifest 冒充同一候选。

### R71-20：四臂 repeat-10 与 held-out

- 类型：产品评测。
- 入口：R71-19 已关闭且候选未漂移。
- 唯一改动域：Standard、`map-always`、`map-append`、`map-request` 的正式矩阵运行与报告。
- 不包含：运行中修代码、修改样本、选择性丢弃 bad case 和晋升决定。
- 产物：simple/complex 每臂 repeat 10、额外 held-out 的 sealed matrix。
- 预期收益：用足够重复数观察正确率、行为稳定性和成本分布，而非单次偶然结果。
- 独立验收：正确率、request、token、cache、wall time、Tool schema 和 Map 形状均可从 raw artifacts 重算。
- 退出：矩阵完整、无 provenance/eligibility finding、异常 trace 已逐项归因。
- 回退：不改生产行为；运行中候选或环境漂移则整轮作废并回到 R71-19。

### R71-21：产品晋升决策

- 类型：用户决策。
- 入口：R71-20 已关闭。
- 唯一改动域：基于 sealed matrix 的产品代价、收益和残余风险裁决。
- 不包含：隐藏修复、自动晋升和用成本掩盖正确性回归。
- 产物：用户明确批准、拒绝或要求新一轮原子修复的记录。
- 预期收益：工程证据与产品取舍分离，Runtime 不替用户决定策略是否晋升。
- 独立验收：结论引用唯一 candidate、完整四臂数据、held-out 和所有残余风险。
- 退出：用户明确决策后才允许更新 R7.1 acceptance baseline。
- 回退：未批准即不晋升；不存在自动 fallback。

## 4. 依赖与并行批次

批次不是 Phase，不拥有状态，也不能整体宣告关闭。每个编号必须单独提交、测试和记录证据。

```text
首批可并行：
  R71-01  R71-02  R71-03  R71-04  R71-05  R71-06  R71-07

R71-07 -> R71-08
R71-01 -> R71-09
R71-01 -> R71-10 -> R71-11

R71-01..05 + R71-09..11 -> R71-12
R71-12 -> [仍复现] R71-13 -> R71-14
R71-12 -> [不复现] R71-13/R71-14 不触发关闭

R71-09 + R71-12 + R71-14(或不触发) -> R71-15
R71-08 + R71-12 + R71-14(或不触发) -> R71-16
R71-08 + R71-11 + R71-14(或不触发) -> R71-17

R71-01..17 -> R71-18 -> R71-19 -> R71-20 -> R71-21
```

实施纪律：

1. 每次只把一个 `R71-xx` 标记为 `实施中`；无写冲突的首批单元可以由独立 worktree/subagent 并行，但分别提交；
2. 决策 Phase 只产出决策证据，不得夹带生产实现；
3. 复验 Phase 只回答现象是否存在，不得顺手修复；
4. 实现 Phase 不得依赖后续成本或正式评测才能证明自身正确；
5. 上游关闭后，下游先重跑旧失败；现象消失则关闭条件 Phase，不机械执行旧方案；
6. 任一 Phase 需要第二根因、第二生产模块或第二用户决策时必须再拆编号。

## 5. 通用验收纪律

1. 每个实现 Phase 必须有根因记录、生产路径测试、反例测试、结构化日志和独立关闭记录；
2. 测量 Phase 不得修改被测语义，反馈 Phase 不得替 Agent 决策，Runtime Phase 不得解释 Tool 业务内容；
3. 日志至少携带 request/call/map/revision 或对应 artifact identity、成功状态、失败状态和 reason code；
4. 单元测试只关闭工程门；真实模型遵循、成本和缓存必须使用同口径 Docker sample；
5. 每次只改变一个可归因策略；不得把多个 Phase 合并到一个 candidate 后再倒推收益；
6. fresh adversarial review 只复审发生变更的独立 shard，并检查相邻约束无回归；
7. 任一失败不得恢复旧 wire、双 parser、rollout fallback、current node、普通 Tool decoration 或兼容分支；
8. Phase 关闭后才更新本清单状态；后续失败只能把原 Phase 改为 `返修` 或新增真正独立的原子 Phase。
