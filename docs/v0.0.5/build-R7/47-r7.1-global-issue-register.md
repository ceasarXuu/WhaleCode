## 2. 维护规则

1. 每个问题使用稳定 ID `R71-GI-xxx`，不得复用或重编号；
2. 新发现的问题必须先与现有条目去重，再决定新增、补充证据或拆分；
3. 同一问题的不同表现写入同一条目的 Symptoms，不重复建账；
4. 同一实现造成两个独立验收失败时可以拆分，例如 revision 语义正确性与 Provider 缓存正确性；
5. 状态只允许：
   - `open-confirmed`：问题和主要因果已由证据确认；
   - `open-investigating`：问题确认，但根因尚未收敛；
   - `implementing`：修复方案已批准并正在实施；
   - `validating`：实现完成，等待真实样本验收；
   - `closed`：关闭标准全部满足；
6. 单元测试只能证明工程接线，不能单独关闭真实模型行为或成本问题；
7. 问题关闭后保留原 ID，移入本文件的关闭记录，不删除历史；
8. `P0/P1` 表示问题严重度，`执行序` 表示受依赖关系约束后的实际处理顺序，两者不得混用；
9. 修改问题数量、优先级、执行序、依赖、状态、根因或关闭标准时，必须同步更新 `Updated` 和变更记录。

### R71-GI-001：response-final revision 存在双重权威

- Priority: P0
- Status: open-confirmed
- Symptoms:
  - control prepare 返回 `revision_after=N`；
  - sibling result attribution 后 canonical Map 已推进到 `N+K`；
  - 独立 receipt/projection 返回最终 revision，但 Agent 仍使用 prepare revision；
  - rerun 中 14 个 response stale 和 3 个 `finish_map` stale 全部符合该路径。
- Root cause:
  - 中间 revision 与最终 revision 同时作为成功事实进入上下文；
  - 最终值没有收敛为同一个 `taskspace_control` Tool result 中唯一可用于下一次提交的 revision。
- Boundary:
  - Runtime 只反馈机械 revision 事实；
  - Runtime 不替 Agent 选择动作或自动修复提交。
- Close criteria:
  - sibling attribution 完成后，同一 control Tool result 返回唯一权威 `canonical_revision`；
  - 中间值如需保留，只能使用明确的诊断名称，不能与下一提交 revision 竞争；
  - 三种 projection policy 的同口径 repeat-3 中，隐藏 result attribution 导致的 stale 为 0；
  - 普通 Tool 原生输出保持不变。

## 7. 依赖关系与优先级

### 7.1 依赖类型

- **实现依赖**：前置问题未形成稳定合同前，后置问题不得进入产品实现，避免产生冲突设计；
- **验收依赖**：可以提前分析或开发，但前置问题关闭前不得宣告后置问题关闭；
- **重评依赖**：前置问题关闭后必须先重跑并重新判断现象是否仍存在，不能直接沿用旧根因实施修复。
