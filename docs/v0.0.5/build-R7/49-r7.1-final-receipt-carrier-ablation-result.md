# R7.1 Final Receipt carrier 单变量消融结果

- 日期：2026-07-31
- 对应 Phase：R71-11
- 运行授权：`WAR-20260731-R71-RECEIPT-ABLATION-001`
- 状态：因果贡献已确认 / 生产修复未实施 / R71-11 仍开放

## 1. 实验问题

此前历史版本对照表明，`TaskSpaceResponseFinalReceiptV1` 进入自然历史后与缓存下降高度相关，但引入
该 carrier 的提交同时包含其他改动，不能据此宣称单一根因已经确认。

本轮使用同一源码、同一二进制、同一复杂样本和同一 provider 时间窗口，只改变一个变量：

- control：保留 response-final receipt 的独立 developer carrier；
- ablation：仍计算 receipt、提交 Map 状态并记录遥测，但不把该独立消息写入 Agent 历史。

临时消融开关已在实验后删除，不属于生产设计。

## 2. 运行结果

| 指标 | Control | Carrier ablation | 差异 |
|---|---:|---:|---:|
| 业务结果 | 通过 | 通过 | 无回归 |
| 隐藏 oracle | 通过 | 通过 | 无回归 |
| Provider requests | 9 | 10 | +1 |
| Input tokens | 164,447 | 207,603 | +26.24% |
| Cached input | 63,872 | 130,688 | +66,816 |
| Uncached input | 100,575 | 76,915 | -23.52% |
| Output tokens | 5,685 | 7,995 | +40.63% |
| Request 2+ cache hit | 33.60% | 60.52% | +26.91 pp |
| Agent wall time | 50,709 ms | 67,434 ms | +32.98% |
| 估算费用 | ¥0.11322 | ¥0.09552 | -15.64% |
| Final Receipt wire count | 最终累计 6 | 0 | -6 |
| 最终 system message count | 10 | 6 | -4 |

总 input、request 和 wall time 不能作为 carrier 的净性能结论：消融臂额外发生了 1 次 sequence preflight
failure 和 3 次 state rejection，control 只有 1 次 control failure。缓存、wire role 和 receipt count 才是
本轮单变量的主验收信号。

## 3. 因果结论

Final Receipt 独立 carrier 是当前缓存回归的一个已确认因果因素：

1. control 从第二次请求起持续携带新增 system receipt，request 2+ 命中率为 33.60%；
2. 同一二进制仅停止写入该 carrier 后，wire receipt count 精确降为 0；
3. request 2+ 命中率提高 26.91 个百分点，uncached input 即使在多一次请求和更多失败反馈下仍减少
   23,660 token；
4. 两臂业务结果和隐藏 oracle 均通过。

仅按 schema 名称表述时，“Final Receipt 是全部低命中的唯一根因”被否定；进一步与 pre-receipt
90%+ 版本比较后，Final Receipt 和剩余 failure carrier 被统一到同一根因：动态 Tool 事实被重复提升为
developer/system carrier。消融臂仍未恢复 pre-receipt 历史臂的 86.51%：

- 基础 system message 为 2 条；
- 消融臂随后新增 4 条 system message；
- rollout 逐条证明它们分别来自 1 次 `ToolSequencePreflightResultV3` 和 3 次
  `TaskSpaceResponseCommitFailureV3` 的独立 developer 副本；
- 对应请求的缓存再次下降，而无新增 failure carrier 的稳定段可恢复到 91.57%、95.32% 和 92.63%。

这不是新的未知问题，也不是另一个无关根因，而是 R71-01 direct failure carrier、R71-09 state
rejection feedback 与 R71-11 Final Receipt 共享同一个错误 carrier 抽象。

## 4. 与 90%+ 版本的 Prompt 结构对比

| 结构 | Pre-receipt 90%+ | 当前 carrier ablation | 判断 |
|---|---:|---:|---|
| Base Instructions | 4,792 tokens | 4,792 tokens | SHA-256 完全相同 |
| Core Protocol | 818 tokens | 904 tokens | +86，不足以解释下降 |
| Tools | 6,706 tokens | 6,792 tokens | +86，不足以解释下降 |
| 固定 system 数 | 2 | 2 | 相同 |
| 动态 system 数 | 0 | 最终累计 4 | 唯一结构性差异 |
| 无新增动态 system 的当前请求 | 不适用 | 91.57%、95.32%、92.63% | 可恢复 90%+ |
| 新增动态 system 后的当前请求 | 不适用 | 38.76%、35.65%、28.91%、23.50% | 立即下降 |

当前四条动态 system 的 content SHA-256，都与同一事实先前已经返回的 Tool output 完全相同。90%+
版本始终保持：

```text
system, system, user/assistant/tool 自然追加
```

当前失败路径则变成：

```text
..., tool[, tool], system, user
```

因此完整根因不是 prompt 更长、协议版本变化或 Tool schema 增加 86 tokens，而是反馈层把 Tool result
重复写成独立 developer message，provider 再将它转成对话中段 system。

## 5. 工程决定

1. R71-11 的根因证据门已满足，但 Phase 不能关闭，因为生产 carrier 尚未迁移；
2. 不允许直接删除 receipt 事实。先由 R71-10 将唯一 canonical final revision 纳入原生 control result，
   再由 R71-11 删除独立 developer/system receipt；
3. R71-01 和 R71-09 必须同时消除失败事实的额外 developer/system 副本，只保留原生 Tool result；
4. 完成三项修复前，不能把剩余缓存损失归因于 projection policy，也不能执行正式成本晋升。

## 6. 全动态 Carrier 单样本验证

用户追加批准 1 个复杂 sample 后，在同一当前版本执行更严格的诊断：统一过滤 Tool sequence 产生的
所有独立 `ResponseInputItem::Message`，同时保留原生 Tool results、Map 状态和工具执行。

| 指标 | Current control | Receipt-only ablation | All dynamic carrier ablation | Pre-carrier fresh |
|---|---:|---:|---:|---:|
| Request | 9 | 10 | 9 | 11 |
| Request 2+ cache | 33.60% | 60.52% | 84.85% | 86.51% |
| Cached input | 63,872 | 130,688 | 147,456 | 170,496 |
| Uncached input | 100,575 | 76,915 | 24,157 | 37,622 |
| System messages/request | 2→10 | 2→6 | 始终 2 | 始终 2 |
| 业务与隐藏 oracle | 通过 | 通过 | 通过 | 通过 |

全 carrier 消融较 current control 提升 `51.25 pp`，与同日 pre-carrier fresh baseline 只差 `1.66 pp`。
它没有达到 retained 历史多次运行的 91.9%～92.5%，但 provider 缓存是 best-effort，且本轮动作路径和
feedback 长度不同。关键因果门全部满足：

1. 9 次请求始终只有 2 条固定 system；
2. 两次 control failure 仍通过原生 Tool result 忠实返回，但不再生成动态 system；
3. 业务结果、Map 和隐藏 oracle 保持正确；
4. 缓存恢复到同日、同 provider 的 pre-carrier fresh 基线范围。

因此 H-004 的完整根因得到运行验证。该诊断不能直接作为生产修复：统一出口过滤会隐藏未来可能合法的
Message carrier。生产实现仍需在各事实产生位置删除重复副本，并先完成 canonical final revision 的原生
Tool result 承载。
