## 4. 状态反馈复验

旧 blocker 的关键反例是：同事务将 Work 临时完成后又向它声明动作，失败反馈只给
`actual_state=completed`，Agent 将其误认为 canonical 已提交。当前合同改为：

- `canonical_state_before_transaction`
- `evaluated_state_at_violation`
- `allowed_states_at_violation`
- canonical/evaluated 两套未满足前驱

聚焦测试稳定得到 canonical `ready`、evaluated `completed`、`state_commit=false`。本次正式矩阵有 7 个
`node_state_invalid` request，均为 canonical/evaluated 同为 `waiting`，没有自然触发两套状态不同的事务，
因此 live 证据只能证明字段在生产路径中完整存在，不能替代该反例的确定性回归。

7 个 Waiting 拒绝中，3 个下一请求直接完成前驱并继续，4 个 `map-request` 下一请求显式 `read_map`。这 4 份
拒绝已经直接携带 canonical/evaluated=`waiting`、未满足前驱和 canonical revision；read 后 Agent 只是确认同一
事实并继续。该行为可能是外部 Map 模式下的保守读取，也可能表示字段显著性仍不足，交由 fresh reviewer 尝试证伪。
无论结论如何，都不得通过 Runtime 建议、自动改绑或自动状态推进解决。

evaluated state 误认为 canonical state。修复只能补全机械状态域，不得通过 Runtime 建议、自动改绑或替
Agent 选择节点来掩盖问题。
