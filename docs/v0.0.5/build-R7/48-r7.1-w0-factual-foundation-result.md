## 1. 阶段结论

前三轮对抗性审查累计接受的 blocking finding 已完成工程修复。Round 2 指出的
candidate/canonical 状态域、provider attempt 全集、ToolSearch/普通 Tool carrier、重复输出与 provenance
问题均有正反回归。随后两次正式矩阵又暴露并收敛了两个观测链缺口：

1. Agent 未完成或被中断的真实观察不得被 harness 删除；只要原始证据完整，就继续封存并以
   `comparison_eligible` 区分，符合 C-14；
2. provider response 的 supplemental 出现在 `token_count` 之后时，不能按遍历位置绑定到下一请求；
   observer 现由 `affected_call_ids` 反查唯一 owning request，并要求 call 集合精确相等。

Round 3 又发现三个实现完整性缺口：真实 `ToolSearchFailureV3` producer 与 observer 的 provenance
合同漂移、缺少 state rejection + ToolSearch 的精确组合回归、TaskSpace MCP fixture 不是完整生产形态。
修复候选统一了生产 ToolSearch provenance，补上真实状态机 complete/reserve 冲突与 ToolSearch sibling
回归，并让 Standard/TaskSpace 与 metrics fixture 都使用 namespaced Function MCP 形态。

Round 4 replacement reviewer 又找出四个阻断缺口：supplemental failure 对畸形/未知/残缺结构仍可能
fail-open；state rejection + ToolSearch 测试未穿过异步生产入口；ToolSearch provenance 仍从错误文本推断
来源；结果文档的状态拒绝数量和后续 `read_map` 数量已经与工件不一致。当前提交已完成对应修复：

1. supplemental failure 的结构、布尔失败语义、角色、scope、affected call 集合和 ToolSearch cause
   全部 fail-closed；
2. 组合回归穿过 `execute_response_tool_sequence`，并以 poisoned dispatch 证明拒绝发生在零执行之前；
3. provider-response rejection 与 ToolSearch execution failure 使用不同的 typed 生产分支，不再解析
   `error.message` 决定来源；
4. 矩阵自动输出被拒请求数、违规事实数、canonical/candidate 状态对和下一请求动作，文档不再人工统计。

当前提交 `50c2b77d1` 的 24-run 矩阵已通过严格 report/provenance gate。GI-005、GI-007 仍只处于
`validating`；必须由另一名无上下文 reviewer 对本次修复执行 fresh replacement review，通过前不得关闭，
也不得进入 W1。

## 4. 状态反馈复验

旧 blocker 的关键反例是：同事务将 Work 临时完成后又向它声明动作，失败反馈只给
`actual_state=completed`，Agent 将其误认为 canonical 已提交。当前合同改为：

- `canonical_state_before_transaction`
- `evaluated_state_at_violation`
- `allowed_states_at_violation`
- canonical/evaluated 两套未满足前驱

聚焦测试稳定得到 canonical `ready`、evaluated `completed`、`state_commit=false`。本次正式矩阵自动汇总出
11 个 `node_state_invalid` request 和 11 份违规事实：

| arm | 请求 | 状态对（违规数） | 下一请求 `read_map` |
|---|---:|---|---:|
| map-always | 2 | `completed->completed:1`、`ready->completed:1` | 0 |
| map-append | 4 | `absent->waiting:1`、`waiting->waiting:3` | 0 |
| map-request | 5 | `absent->waiting:2`、`waiting->waiting:3` | 2 |

这里的箭头只表示 `canonical_before_transaction -> rejected_candidate_at_violation`，不是状态迁移。矩阵自然
触发了 `ready->completed` 和 `absent->waiting`，证明两套状态域在 live 路径中可见。11 个请求中只有
2 个 `map-request` 下一请求显式 `read_map`，其余直接继续执行；是否仍存在 Agent 误读由 fresh reviewer
结合原始 trace 裁决。无论结论如何，都不得通过 Runtime 建议、自动改绑或自动状态推进解决。

Agent 选择节点来掩盖问题。
